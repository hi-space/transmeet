# 회의 대화를 별도 테이블로 분리 — 설계

## 배경과 이유

회의 대화는 지금 `transmeet-meetings` 의 회의 항목 하나 안에 `messages` 리스트로 쌓인다
(`backend/app/ws_handler.py` 의 `list_append` 두 곳). 2026-10-28 실측으로 확인한 문제:

1. **대화가 사라진다.** 메시지 1,156개짜리 회의 항목이 DynamoDB 항목 한도 400 KB 에 닿았다.
   WS 백엔드 로그에 `Item size has exceeded` 가 10/7 114건, 10/9 3건 — 117개 발언이 저장되지 않았다.
   화면에는 보였지만 회의를 다시 열면 없다. 대략 메시지 1,000개를 넘는 회의는 모두 같은 일을 겪는다.
2. **목록이 느리다.** `GET /meetings` 는 한 줄 요약·녹음 여부를 읽으려고 기본 테이블을 BatchGet 하는데,
   `ProjectionExpression` 과 관계없이 항목 전체를 읽는다. 회의 122개에 약 1,800 RCU, 4–5회 왕복(UnprocessedKeys 재시도),
   1.3–1.85초. Lambda p95 약 1.6초와 일치한다.
3. **쓰기가 비싸다.** 메시지 한 줄을 붙일 때마다 항목 전체 크기만큼 WCU 를 쓴다(300 KB 회의면 약 300 WCU).

세 문제 모두 "늘어나기만 하는 리스트를 한 항목에 쌓는" 구조에서 나온다. 메시지마다 항목을 하나씩 두면 함께 사라진다.

## 목표

- 회의 길이와 상관없이 모든 발언이 저장된다.
- 회의 항목은 메타데이터만 담아 몇 KB 로 유지된다. 목록 BatchGet 이 작은 항목만 읽는다.
- 메시지 쓰기 비용이 회의 길이와 무관하다.
- 기존 124개 회의의 대화가 빠짐없이, 같은 순서로 옮겨진다.
- 프런트엔드는 바꾸지 않는다 — `GET /meetings/{id}` 응답의 `messages` 배열 모양을 유지한다.

## 비목표

- 이미 저장 실패한 117개 발언 복구(DB 에 없다. 로그에 원문이 남았는지는 별도 확인 거리).
- 목록용 새 GSI(앞서 논의한 방법 A). 이 작업 뒤 목록 시간을 다시 재고 필요하면 따로 한다.
- 죽은 코드 `infra/lambda/ws-audio`(스택에서 참조하지 않음) 정리.
- 메시지 수정·삭제 기능. 지금처럼 추가만 한다.

## 안티골 (돌아가도 실패인 것)

- 옮기는 도중이나 뒤에 메시지가 하나라도 빠지거나 순서가 바뀐다.
- 남의 회의 메시지가 보인다(소유 확인은 지금처럼 회의 항목의 `userId` 로 한다).
- 삭제된 회의의 메시지가 남거나, 없는 회의에 메시지가 생긴다(지금의 `attribute_exists(meetingId)` 보호를 잃는다).
- 전환 후 목록·상세 조회가 지금보다 느려진다.

## 제약

- 녹음 중인 회의가 없을 때 한 번에 전환한다(사용자 결정). 두 곳에 같이 쓰는 이행 기간은 두지 않는다.
- 회의 테이블은 PITR 켜짐, `RemovalPolicy.RETAIN`. 원본 `messages` 는 검증 뒤에만 지운다. PITR 이 마지막 안전망.
- 백엔드 배포는 `deploy.sh` 에 없다: 고유 태그로 이미지 푸시 → `cdk deploy -c wsImageTag=<태그>`, `--platform linux/amd64`.
- 같은 작업 트리를 다른 세션이 함께 쓴다. 바꿀 파일(`ws_handler.py`, `page_agent.py`, `infra/lambda/meetings/index.ts`,
  `infra/lambda/summarize/index.ts`, `transmeet-stack.ts`)에 이미 커밋되지 않은 변경이 있다. 시작 전에 그 변경의 주인을 확인한다.

## 접근 방식

| 방식 | 장점 | 단점 |
|---|---|---|
| **1. 새 테이블, 메시지 하나당 항목 하나 (선택)** | 쓰기 1회·항상 1 WCU, 길이 한도 없음, Query 한 번에 시간순 | 긴 회의를 읽을 때 항목 수만큼 읽음(1,000개 ≈ 1 MB, 1–2회 왕복) |
| 2. 새 테이블, 메시지 100개 묶음 항목 | 읽기 왕복 적음 | 묶음 카운터·꽉 참 확인·동시 쓰기 경합 처리 필요. 이 규모에선 복잡함이 더 큼 |
| 3. S3 에 회의별 파일 | 저장 단가 낮음 | 이어 쓰기 불가 — 발언마다 객체를 다시 쓰거나 발언마다 객체가 생김 |

기존 회의 테이블에 정렬 키를 더하는 단일 테이블 방식은 불가능하다(키 스키마는 바꿀 수 없다).
사용자는 방식 1을 골랐다. 단순하고 쓰기 경로에 상태가 없다.

## 결정한 것

### 테이블 `transmeet-messages`

- 파티션 키 `meetingId`(S), 정렬 키 `sk`(S) = `{timestamp}#{id}`.
  `timestamp` 는 지금 메시지에 있는 ISO 문자열 그대로, `id` 는 메시지 id. 같은 시각 충돌을 id 가 가른다.
- 속성: 지금 메시지 맵의 필드 그대로 — `id, speaker, originalText, translatedText, detectedLanguage, timestamp`.
- 온디맨드, PITR 켜짐, `RETAIN`. 회의 테이블과 같은 역할(Lambda 역할, WS 태스크 역할)에 읽기·쓰기 권한.
- 정렬 키가 내용에서 정해지므로 같은 메시지를 다시 넣어도 덮어쓸 뿐이다 → 이전 스크립트를 여러 번 돌려도 안전하다.

### 쓰기 (WS 백엔드 두 곳)

`list_append` 업데이트를 `TransactWriteItems` 하나로 바꾼다.
- 메시지 테이블에 `Put`
- 회의 항목에 `Update`: `ADD messageCount :one`, `SET updatedAt`, 조건 `attribute_exists(meetingId)`

조건이 실패하면 트랜잭션 전체가 취소돼 유령 메시지가 생기지 않는다(지금의 보호와 같다).
취소 사유가 조건 실패면 지금처럼 경고 로그만 남긴다. 작은 항목 2개라 트랜잭션 비용은 몇 WCU 다.

### 읽기

메시지 테이블을 `meetingId` 로 Query(정렬 키 오름차순, `ConsistentRead=True`, 페이지를 끝까지 이어 받기)해
지금과 같은 모양의 배열로 돌려주는 도우미를 두 언어에 하나씩 둔다.
- Python: 백엔드 공용 모듈 — 요약(WS 경로, `ws_handler.py` 저장 메시지 경로), 페이지 에이전트(`page_agent.py` 의 `_load_meeting` 이 회의 항목에 `messages` 를 붙여 돌려줌 → `build_meeting_payload` 무변경)
- TypeScript: `infra/lambda/shared/` — 상세 조회(`GET /meetings/{id}` 가 응답에 `messages` 를 붙임), 제목 생성(앞 20개만 → `Limit` 사용), 요약 Lambda

페이지 에이전트는 종료 직후 마지막 발언까지 읽어야 해서 강한 일관성 읽기가 필요하다. 다른 경로도 비용이 작아 같은 설정을 쓴다.

### 생성과 삭제

- `POST /meetings` 는 회의 항목에 `messages: []` 를 더는 넣지 않는다. 응답에는 프런트 호환을 위해 `messages: []` 를 붙여 돌려준다.
- `DELETE /meetings/{id}` 는 **메시지를 먼저** 지운다(Query 로 키 수집 → BatchWrite 25개씩, 미처리분 재시도). 그다음 회의 항목.
  중간에 실패해도 회의가 남아 있어 사용자가 다시 지울 수 있다. 순서를 반대로 하면 주인 없는 메시지가 남는다.

### 이전과 전환 순서

1. **배포 1 — 테이블만.** CDK 로 `transmeet-messages` 와 권한을 만든다. 코드는 아직 옛 방식.
2. **복사.** 이전 스크립트가 회의 테이블을 스캔해 각 `messages` 를 메시지 테이블에 BatchWrite 한다. 원본은 건드리지 않는다.
3. **배포 2 — 코드 전환.** 녹음 중인 회의가 없을 때 Lambda 와 WS 백엔드를 새 코드로 배포한다.
4. **다시 복사.** 같은 스크립트를 한 번 더 돌려 1–3 사이에 들어온 발언을 채운다(덮어쓰기라 중복 없음).
5. **검증.** 회의마다 원본 `messages` 의 id 집합 = 메시지 테이블 Query 의 id 집합, 개수 일치. 하나라도 다르면 멈춘다.
6. **원본 제거.** 들어가기 전에 ECS 서비스에 새 태스크 정의만 돌고 있는지(배포 1개, 옛 태스크 0개) 확인한다.
   그다음 검증을 통과한 회의만 `REMOVE messages` 하되, 조건 `size(messages) = :검증한개수` 를 건다.
   그사이 옛 코드가 한 줄이라도 붙였으면 조건이 실패해 원본이 남고, 스크립트는 그 회의를 다시 복사·검증하라고 보고한다.
   같은 업데이트에서 `messageCount` 를 검증한 개수로 다시 쓴다.
   이 단계 뒤 항목이 작아져 목록이 빨라진다.

`messageCount` 는 빈 회의 자동 정리(`src/app/page.tsx` `isPrunable`, `messageCount === 0`)의 근거라 틀리면 회의가 지워질 수 있다.
2026-10-28 조사에서 124개 회의 모두 실제 메시지 수와 일치했고, 값이 없는 1개는 메시지도 0개였다. 6단계에서 다시 써서 그 상태를 확정한다.

2–5 동안 사용자에게 빈 회의가 보이는 구간이 없다. 새 코드가 켜지기 전에 이미 복사본이 있다.
스크립트는 저장소에 남긴다(`scripts/` 아래, 드라이런 기본, 실행은 명시 옵션).

### 순서 — 조사 결과 (2026-10-28, 전체 125개 항목·33,008개 메시지)

- `timestamp` 형식은 전부 `YYYY-MM-DDTHH:MM:SS.ffffff+00:00` 하나다(Python `isoformat()`). 문자열 정렬 = 시각 정렬. 빠진 필드·중복 id 없음.
  마이크로초가 0 이면 `isoformat()` 이 소수부를 생략하지만(`…:56+00:00`), `+`(0x2B) 가 `.`(0x2E) 보다 앞이라 같은 초의 다른 값보다 먼저 정렬돼 순서가 맞는다.
  메시지를 쓰는 곳은 Python 백엔드뿐이다(JS `toISOString()` 의 `Z` 형식이 섞일 경로 없음). 정규화하지 않는다.
- **배열 순서와 시각 순서가 어긋난 메시지가 94개 회의에 470개** 있다(차이 중앙값 1.2초, p90 4.5초, 최대 29초).
  시각은 발화 구간을 넘길 때 찍히고(`_iso_now()`), 번역은 병렬 태스크라 끝난 순서대로 `list_append` 되기 때문이다.
- 프런트는 이미 불러올 때 시각순으로 다시 정렬한다(`src/lib/api.ts` `toMeeting`). 반면 요약·제목·페이지는 지금 배열 순서(=번역 완료 순서)를 쓴다.

결론: 정렬 키 `{timestamp}#{id}` 를 유지한다. 모든 경로가 화면과 같은 발화 순서를 받게 되므로 요약·페이지 쪽은 오히려 바로잡힌다.
같은 시각(한 번에 넘긴 구간의 여러 화자) 사이 순서는 id(생성 ms + 무작위 5자)로 정해지는데, 지금도 완료 순서라 임의적이었으므로 잃는 것이 없다.
프런트 정렬은 그대로 두어도 무해하다.
**안티골의 "순서가 바뀐다" 는 화면에 보이는 순서 기준이다.** 이전 검증(5단계)은 배열 순서가 아니라 id 집합 일치 + 개수 일치로 한다.

## 빌더에게 맡기는 것

- 이전 스크립트 언어(Python 또는 TS)와 진행 출력 형식
- 테스트 구성. 기존 `backend/tests`(`test_page_agent_run`, `test_stream_summary`, `test_meeting_end` 등)와
  `tests/*.mjs` 에서 `messages` 를 회의 항목에 넣는 가짜 데이터를 새 구조에 맞게 고친다.
