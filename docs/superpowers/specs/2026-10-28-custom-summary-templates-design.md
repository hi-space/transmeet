# 내 양식 — 사용자별 커스텀 요약 프롬프트 설계

작성일: 2026-10-28

## 의도

요약 방식은 지금 네 가지(자세하게 · Amazon 미팅록 · 의사결정 기록 · 공유·보고용)가 고정으로 있다. 하지만 팀마다 이미 쓰는
회의록 양식이 있어서, 고정 방식으로는 결국 다 맞출 수 없다. 사용자가 **자기만의 요약 양식을 저장해 두고** 기본 방식처럼
골라 쓰게 한다. 오늘 실험에서 확인한 것처럼, 형식이 달라져도 **근거와 영향이 남는 깊이**는 유지되어야 한다(사용자가
"결과만 나열해서 얕다"며 간결하게·할 일 중심 두 방식을 지웠다).

## 사용자 결정

- **본인 전용.** 공유나 팀 양식은 만들지 않는다. 기존 사용자 격리(Cognito `sub` = `userId`) 안에서 끝난다.
- **서버 저장 + 기기 간 동기화.** 양식은 이름을 붙여 저장하고 어느 기기에서든 드롭다운에 보인다.
- **입력 방식 두 가지.**
  - 지시문 작성: 원하는 형식을 말로 설명한다.
  - 기존 회의록 붙여넣기: 예시를 붙이면 그 **구조와 톤만** 따르고, 예시의 내용은 옮기지 않는다.
- **적용 범위.** 수동 요약, 자동 요약(사용자 설정 `autoSummarizeMessageCount` 간격), 회의 종료 요약과 메일 모두에 적용한다.
  사이드바의 한 줄 요약(`useMeetingBrief`, 대화 20개마다)과 미팅 페이지에는 적용하지 않는다.
- **미리보기는 이번 범위에서 뺀다.**
- **방식 B를 택했다.** 회의에서 양식을 고르는 순간 양식 사본을 회의 레코드에 복사한다(아래 "검토한 방식" 참고).

## 목표 · 비목표 · 반목표

- 목표: 양식 생성·수정·삭제, 회의별 선택, 세 생성 경로(WS 수동·자동, 회의 종료, REST Lambda 폴백) 모두 같은 결과,
  생성된 요약에 어떤 양식으로 만들었는지 표시.
- 비목표: 공유, 미리보기, 양식 버전 이력, 양식별 모델·길이 선택, 미팅 페이지(에이전트) 적용, 양식 가져오기·내보내기.
- 반목표(기술적으로 동작해도 실패로 본다):
  - 커스텀 양식 때문에 트랜스크립트에 없는 사실, 담당, 수치가 생기는 것.
  - 붙여 넣은 예시 회의록의 내용(이름, 수치, 결정)이 요약에 섞여 들어가는 것.
  - 다른 사용자의 양식이나 사본을 읽거나 쓸 수 있는 것.
  - 기존 네 방식의 프롬프트와 출력이 바뀌는 것.

## 현재 구조 (바뀌는 지점)

- 회의 레코드(`transmeet-meetings`)의 `summaryStyle` 문자열이 선택값이다.
  - `PUT /meetings/{id}/summary-style`(`infra/lambda/meetings/index.ts:284`)가 `isSummaryStyle`로 검증해 저장한다.
  - 모델은 호출하지 않는다.
- 생성 경로는 세 가지이고, 모두 `backend/app/summary_styles.json`을 읽는다.
  - WS `summarize`: `_stream_summary`, `ws_handler.py:1196`. 요청의 `summaryStyle`이 있으면 우선하고, 없으면 회의 레코드
    값을 쓴다. 자동 요약도 이 경로다.
  - WS 회의 종료: `_end_meeting`, `ws_handler.py:1439`. 내부에서 `_stream_summary`를 부르고 결과를 메일로 보낸다.
  - REST 폴백: `infra/lambda/summarize/index.ts`. `infra/lambda/shared/summaryPrompt.ts`로 같은 JSON을 읽는다.
- 알 수 없는 방식 값은 세 곳(Python `normalize_summary_style`, TS `normalizeSummaryStyle`, 프런트) 모두 `detailed`로 바뀐다.
- 사용자 단위 저장소는 없다. 테이블은 meetings와 pages뿐이고, 설정은 브라우저 localStorage(`useSettings.ts`)에 있다.
  사용자 단위 API의 선례는 `/me/email`(`EmailFn`, `transmeet-stack.ts:286`)이다.
- 메일 렌더러(`mailer.py summary_to_html`)는 제목, 불릿, 굵게, 표, 문단만 지원한다. 중첩 불릿은 평평해지고
  체크박스는 글자 그대로 나온다.

## 검토한 방식

| 방식 | 내용 | 득실 |
|---|---|---|
| A. ID 참조 | 회의에 `custom:<id>`만 두고 생성할 때마다 양식 테이블 조회 | 수정이 즉시 반영되지만 세 경로 모두에 조회가 들어간다. 양식을 지우면 조용히 `detailed`로 바뀌고, 무엇으로 만들었는지 남지 않는다 |
| **B. 선택 시 복사 (채택)** | 양식 목록은 테이블에 두고, 회의에서 고를 때 사본을 회의 레코드에 저장 | 생성 경로는 원래 읽던 회의 레코드만 본다. 삭제·수정에도 진행 중인 회의가 깨지지 않는다. 수정을 반영하려면 다시 선택해야 한다 |
| C. 브라우저 저장 | 양식을 localStorage에만 두고 선택 시 사본 전송 | 가장 가볍지만 기기 간 동기화 요구와 충돌해 제외 |

B를 고른 이유: 이 앱은 요약이 사용자 조작 없이 자동으로 여러 번 생성된다. 생성 순간에 외부 상태에 덜 의존할수록 안전하다.

## 설계

### 데이터

- **새 테이블 `transmeet-summary-templates`**
  - PK `userId`(S), SK `templateId`(S, UUID). PAY_PER_REQUEST, 기존 테이블과 같은 RemovalPolicy.
  - 속성:
    - `name`: 1~30자, 사용자 안에서 중복 허용.
    - `kind`: `instruction` 또는 `example`.
    - `body`: `instruction` 1~6,000자, `example` 1~12,000자. 넘으면 400으로 거부하고 자르지 않는다
      (잘라 내면 예시의 구조가 깨진다). 편집기는 글자 수를 보여 주고 넘으면 저장 버튼을 막는다. *(설계자 판단)*
    - `createdAt`, `updatedAt`: ISO 문자열.
  - 사용자당 최대 10개. 생성 시 Query로 개수를 세고, 초과하면 409.
- **회의 레코드에 추가하는 속성**
  - `summaryStyle = "custom"`: 새 값.
  - `summaryCustom = { templateId, name, kind, body, templateUpdatedAt }`: 선택 시점의 사본.
  - `summaryGeneratedLabel`: 요약을 만든 시점의 양식 이름. 기본 방식이면 쓰지 않는다.
  - 기본 방식으로 다시 바꿔도 `summaryCustom`은 지우지 않아도 된다. 생성 경로는 `summaryStyle === "custom"`일 때만 이 값을 본다.

### API

새 Lambda 하나를 둔다(`SummaryTemplatesFn`, `EmailFn`과 같은 패턴, Cognito authorizer). 사용자는 항상 claims의 `sub`로 정한다.

| 메서드 · 경로 | 동작 |
|---|---|
| `GET /me/summary-templates` | 내 양식 목록(이름순 또는 생성순, 빌더 재량) |
| `POST /me/summary-templates` | 생성. 검증 실패 400, 개수 초과 409 |
| `PUT /me/summary-templates/{templateId}` | 수정. 조건식 `userId` 일치, 없으면 404 |
| `DELETE /me/summary-templates/{templateId}` | 삭제. 그 양식을 고른 회의의 사본은 그대로 둔다 |

**회의 선택 API 확장.** `PUT /meetings/{id}/summary-style` 바디로 `{ summaryStyle: "custom", templateId }`를 받는다.

- meetings Lambda가 `(userId, templateId)`로 양식을 **서버에서 직접 읽어** `summaryCustom`에 복사한다.
- 클라이언트가 보낸 본문은 믿지 않는다. 길이 제한과 소유권을 서버에서 보장하기 위해서다.
- 양식이 없으면 404.
- 기존 네 방식 요청은 지금과 같다.
- meetings Lambda에 템플릿 테이블 읽기 권한을 추가한다.
- **양식 수정을 진행 중인 회의에 반영하는 방법.** native `<select>`는 같은 값을 다시 골라도 `onChange`가 발생하지 않는다.
  그래서 "다시 고르기"에 기대지 않는다. 회의 사본에 `templateUpdatedAt`을 함께 저장한다. 현재 회의의 양식이
  사본보다 새로우면 드롭다운 아래에 "양식이 수정됐습니다 · 최신 내용 적용" 링크를 보인다. 누르면 같은
  `PUT /meetings/{id}/summary-style`(`custom`, `templateId`)을 다시 호출해 사본을 갱신한다. 다른 회의를 자동으로
  갱신하지는 않는다. *(설계자 판단)*

### 프롬프트 조립

`summary_styles.json`에 `customWrapper`(지시문용)와 `exampleWrapper`(예시용) 문자열 배열을 추가한다. 그러면 Python과
TS가 같은 정의를 읽고, 기존 Python↔TS 동기화 테스트를 확장해 함께 검증할 수 있다.

조립 순서:

1. 시스템 프롬프트는 기존 것 그대로 쓴다. 이미 형식 중립이고, 트랜스크립트를 데이터로 취급하는 규칙이 들어 있다.
2. 사용자 메시지:
   1. `미팅 제목: …`
   2. 고정 규칙 블록. 사용자 양식으로 덮어쓸 수 없다.
      - 사실은 트랜스크립트에서만 가져온다.
      - 없는 담당, 기한, 수치를 추측하지 않는다.
      - 화자 정보가 없으므로 화자 라벨을 만들지 않는다.
      - 짧게 쓰더라도 근거와 영향은 남긴다.
      - 형식, 섹션, 톤, 길이는 아래 양식을 따른다.
   3. 사용자 양식 본문. `<사용자_양식>…</사용자_양식>` 같은 구분 태그로 감싼다.
   4. `---` 뒤에 트랜스크립트.
- `example`이면 래퍼가 다음을 명시한다.
  - 예시는 형식 견본이다. 구조, 섹션 제목, 톤, 길이감만 따른다.
  - 예시 속 이름, 수치, 결정, 일정은 절대 옮기지 않는다.
  - 예시에 있던 섹션이라도 이번 회의에 해당 내용이 없으면 "해당 없음"으로 둔다.
- 사용자 양식과 고정 규칙이 충돌하면(예: "참석자 이름을 써 줘") 고정 규칙이 이긴다. 이 점을 래퍼에 명시한다.
- 고정 규칙에서 기존 방식들의 "발언 인용 금지"와 "시각 금지"는 뺀다. 사용자가 원하면 써도 된다(빌더 재량이 아니라 이
  설계의 결정). 다만 입력에서 시각을 이미 제거하므로 시각은 어차피 나오지 않는다.

### 생성 경로

- **요청 값과 레코드 값의 우선순위는 지금과 같다.** 프런트는 요청마다 `summaryStyle`을 보내고, 요청 값이 우선한다.
  선택은 저장이 끝난 뒤에 요청되므로(`summaryStyleSavingRef`) 같은 기기에서는 두 값이 같다. 커스텀 요청은 `"custom"`이라는
  값만 보내고 본문은 보내지 않는다. 백엔드는 언제나 레코드의 `summaryCustom` 사본을 쓴다. 다른 기기에서 바꿔서
  오래된 상태가 되는 문제는 기본 방식에도 이미 있는 동작이라 이번 범위에서 바꾸지 않는다. *(설계자 판단)*
- `normalize_summary_style` 계열(Python, TS Lambda, 프런트 `normalizeSummaryStyle` 세 곳 모두)은 `"custom"`을 유효값으로 인정한다. 단, 커스텀으로 실제 생성할 수 있는 조건은
  "회의 레코드에 `summaryCustom`이 있음"이다. 요청이 `custom`인데 사본이 없으면 `detailed`로 만들고,
  `summaryGeneratedStyle=detailed`를 저장한다.
- `_stream_summary`는 메타 조회 프로젝션에 `summaryCustom`을 더한다. 인라인 메시지 경로와 DynamoDB 경로 둘 다다.
  스트림 이벤트와 저장에 `summaryGeneratedLabel`(양식 이름)을 포함한다.
- REST Lambda도 같은 판단과 조립을 한다(`shared/summaryPrompt.ts`).
- 회의 종료 메일은 바뀌지 않는다. 마크다운 요약을 그대로 렌더한다.

### 프런트엔드

- **요약 방식 드롭다운**(`SummaryPanel.tsx`)
  - 기본 네 방식 아래에 `<optgroup label="내 양식">`으로 저장된 양식을 나열한다.
  - 맨 끝에 "내 양식 관리…" 항목을 둔다. 이 항목은 선택값이 아니라 관리 화면을 연다.
  - 현재 회의 사본의 양식이 이미 삭제됐으면 그 회의에서만 "<이름> (삭제된 양식)"으로 보인다.
- **관리 화면**(설정 패널의 새 섹션 + 드롭다운 바로가기)
  - 목록, 새 양식, 수정, 삭제.
  - 편집기 입력: 이름, 종류 토글(지시문 작성 / 기존 회의록 붙여넣기), 본문 textarea와 글자 수(6,000자)를 둔다.
  - 안내 문구: "메일에서는 제목·불릿·표·문단만 그대로 보입니다".
  - 종류별 placeholder 예시를 둔다.
- **표시.** 생성 표시줄("· 공유·보고용" 자리)에 커스텀이면 `summaryGeneratedLabel`을 보인다.
- 양식 목록은 로그인 후 한 번 불러와 캐시하고, 관리 화면에서 바꾸면 갱신한다.
- 회의 선택은 기존 `handleSummaryStyleChange` 흐름을 따른다. 저장 중 잠금, 실패 시 되돌림, 저장이 끝난 뒤 요약 요청까지 같다.

### 검증

- Python
  - 커스텀 조립이 고정 규칙과 구분 태그를 포함하고, 사용자 본문이 그 안에 있는지.
  - 예시 래퍼에 "내용을 옮기지 않는다" 문구가 있는지.
  - 사본이 없을 때 `detailed`로 대체되는지.
  - 스트림 저장에 라벨이 남는지.
- Node
  - 템플릿 CRUD, 다른 사용자의 `templateId`로 선택·수정·삭제하면 404인지.
  - 개수와 길이 제한.
  - 선택 시 서버에서 사본을 복사하고 클라이언트 본문은 무시하는지.
  - Python↔TS 커스텀 프롬프트가 동일한지.
- 실제 모델 확인(배포 전, 오늘 쓴 `/tmp/sumcmp` 방식)
  - 지시문 양식 하나, 예시 양식 하나로 실제 미팅을 돌린다.
  - 예시 내용이 새지 않는지, 근거가 남는지 확인한다.
- 배포는 고유 이미지 태그 + `cdk deploy -c wsImageTag=<태그>` 뒤에 프런트를 올린다. 새 테이블은 CDK가 만든다.

## 기반 상태

요약 방식 관련 파일(`summary_styles.json`, `summaryStyles.ts`, `shared/summaryPrompt.ts` 등)은 아직 커밋되지 않았지만
**운영에 배포된 상태와 같다.** 이 작업은 현재 작업 트리 위에 얹는다. 구현을 시작하기 전에 요약 방식 관련 미커밋 변경을
먼저 커밋해서 기준점을 만든다. 다른 세션의 작업 파일은 커밋에 섞지 않는다(`git add`는 파일을 지정해서).
*(설계자 판단)*

## 빌더에게 맡기는 것
