  2. 10:353분

    온보드 구성 — Jetson Xavier와 Jetson Thor의 역할

    Jetson Xavier는 VCU로 액추에이터 제어와 통신을 맡고, 새로 올리는 Jetson Thor가 관제·주행 플래닝·매핑 같은 상위 연산을 맡아 둘을 RJ45 이더넷으로 잇는 구조다. Jetson Thor 탑재로 전력 분배가 달라져 구동 시간이 줄 수 있다는 우려에는, Jetson Thor 없이 3시간 이상을 보고 있고 YOLO 객체 인식 전용 모델만 올려 전력 소모를 줄이겠다고 답했다.

    [10:35]Jetson Xavier는 약간 VCU 역할을 하는 거예요.

    • 배터리 영향은? → 객체 인식 전용 모델로 전력 절감
    • Jetson Thor 탑재 후 실제 구동 시간은 미확인
  3. 10:383분

    센서 구성과 제조사 현황

    YOLO를 Jetson Thor에서 돌린다면 카메라도 Jetson Thor에 붙어야 빠르지 않냐는 질문이 나왔고, 내장 Depth 카메라는 바닥을 향하고 전면 광각 카메라 두 개로는 인식이 어려워 상부 카메라를 따로 달고 Depth 카메라·고정 LiDAR와 조합하기로 했다. LiDAR는 딜레이를 피하려 Jetson Thor에 직접 연결한다. Ghost Robotics는 데이터를 개방해 준다고 했지만 실제로는 미흡하다는 평가가 나왔고, 중국산을 뺀 기종을 분석해 그나마 나은 곳으로 골랐으며 국내 총판은 KRM이 올해 4월 종료되며 LIG Nex1으로 넘어갔다고 했다.

    [10:38]Depth 카메라가 아래쪽으로 보고 있습니다. 그래서 저희가 카메라를 따로 달려고 하고 있고요.
    • Jetson Thor에 퍼셉션용 상부 카메라 별도 장착
    • LiDAR 등 추가 센서는 Jetson Thor에 직접 연결
    • Ghost Robotics의 실제 데이터 개방 범위
  4. 10:5312분

    저장·SLAM·이동 제어

    Jetson Thor는 개발 키트가 아닌 모듈에 1TB SSD를 쓰고 필요하면 SSD를 추가하며, 자체 통신도 된다. 오도메트리는 시프트 문제로 내부 값을 쓰지 않고 LiDAR 내장 IMU로 하며, FAST-LIO2는 실사용 성능이 떨어져 SLAM을 자체 개발 중이다. 평지·경사 이동은 로봇에 맡기되, 자체 알고리즘에 얹기 위해 가감 제어는 Jetson Thor에서 직접 만들고 계단 전환 때는 모터단까지 제어해야 한다고 했다.

    [11:04]원래는 FAST-LIO2를 생각을 했었는데 … 떨어지더라고요. 실제 활용하기에는. 그래서 저희가 좀 따로 만들고 있습니다.
    • 오도메트리는 LiDAR 내장 IMU로 구성
    • 가감 제어는 Jetson Thor의 자체 로직으로 교체
    • SLAM·내비게이션 모델에 필요한 리소스 규모
    • 계단 전환 시 모터단 제어 방식
  5. 11:162분

    AWS 핵심 서비스

    RL 폴리시만 학습한다면 시뮬레이션에 붙여 학습하면 돼 Amazon SageMaker AI는 이번엔 필수가 아니고, VLA 같은 별도 모델 학습에 MLOps 환경이 필요할 때 쓰며, LLM 서빙은 Amazon Bedrock이 맡는다. 데이터 수집·업로드와 모델 배포 단계가 핵심이어서 AWS IoT Greengrass·AWS IoT Core와 실시간 영상용 Amazon Kinesis Video Streams 세 가지만 기억하면 된다고 정리됐고, 파이프라인은 워크숍으로 실습하길 권했다.

    [11:17]중요한 부분은 1번이랑 4번 부분일 것 같거든요. … 주요되게 제공하고 있는 서비스는 AWS IoT Greengrass랑 AWS IoT Core 두 가지라고 보시면 될 것 같고.
    • 핵심 서비스는 워크숍에서 직접 테스트해 보기로
  6. 11:1818분

    데이터 파이프라인과 레퍼런스 사례

    Amazon S3의 원시 데이터를 Amazon EKS(여러 EC2)로 처리해 다시 저장하고 Amazon SageMaker AI 학습으로 넘기는 레퍼런스가 소개됐고, 어떤 데이터를 취득·폐기하고 타임스탬프를 어떻게 맞출지는 직접 개발할 로직으로 컴퓨터와 스토리지의 위치만 클라우드로 바뀐다고 했다. 비슷한 프로젝트 경험으로 Hive 파티셔닝을 쓴 L0/L1/L2 계층과 Amazon DynamoDB 메타정보 구성이 추가로 설명됐다. WIRobotics(MQTT·Amazon Kinesis Video Streams 수집)와 이동 로봇인 뉴빌리티 사례, 약 4초 지연으로 CCTV처럼 되돌려 보는 재생 기능, Isaac Lab의 학습·시뮬레이션 분리와 Isaac Sim AMI도 다뤄졌으며, LiDAR 데이터는 무거워 온프레미스 처리가 더 빠르다는 의견이 나왔다.

    [11:31]비디오 데이터가 오는 90% 이상은 다 쓸모없는 데이터입니다.
    • 이동 로봇 사례는? → 실시간 영상을 올리는 뉴빌리티 사례
    • LiDAR 데이터 업로드는? → 가능하나 온프레미스가 빠름

    산업안전 로봇 데모

    Unitree Go2가 공장을 돌며 화재·쓰러진 사람·제스처를 감지해 보고서를 만드는 데모로, RGB-D 영상은 Amazon Kinesis Video Streams의 WebRTC로, CPU·메모리·배터리·위치 지표는 MQTT로 올려 Grafana에서 보고, YOLO 모델은 AWS IoT Greengrass로 로봇에 배포하고 ROS 명령은 AWS IoT Core로 원격 제어했다. 대시보드는 직접 개발해야 하고 네트워크가 연결된 상태에서만 동작한다. 판단이 어려운 경우는 에이전트 AI로 Amazon Bedrock의 VLM에 맡겼는데, 시간과 비용을 고려해 엣지 YOLO로 먼저 거르고 confidence가 낮을 때만 VLM에 보내는 방식이 제안됐다. 현장용 파운데이션 모델은 따로 없어 Amazon Bedrock의 여러 모델을 테스트해 고르면 되고, AI가 제어 명령을 직접 만드는 방식도 가능하다고 했다.

    [11:45]confidence 값이 나올 거잖아요. 그게 너무 낮다 하면은 여기 추론을 보내는 형태로 저는 할 것 같아요.

    • 사용자 구축 모델이 필요한가? → 파운데이션 모델 테스트 후 선정
    • VLM의 현장 인식 성능·속도는 테스트 필요
  8. 11:4710분

    Isaac Sim 클라우드 학습

    현 시스템에 맞춰 ROS·Isaac Sim·통신 프로토콜을 세팅한 EC2 하나를 복제해 쓰고, 파라미터는 AWS Batch로 환경 ID·로봇·에폭·GPU 수·이터레이션을 일괄 설정하거나 SSH·Amazon DCV로 개별 제어할 수 있으며, Slurm·AWS ParallelCluster로 직접 제어하는 선택지도 나왔다. 보상·학습 시작·환경 설정을 어떻게 제어할지 고민 중이라는 질문에, 여러 노드의 경험 데이터를 스토리지로 동기화해 모델 하나를 학습하고 로그와 폴리시 동작도 클라우드에서 본다고 답했다. 다만 로컬 PC보다 느려 환경·알고리즘을 PC에서 정의한 뒤 확장 단계에서 클라우드로 옮기길 권했다.

    [11:56]확장시켜서 한꺼번에 테스트를 해야 된다 했을 때 클라우드로 옮기시는 걸 추천드려요.
    • 현 시스템을 Isaac Sim에 구현 가능? → 가능, EC2 하나만 세팅
    • 파라미터 일괄·개별 제어? → 둘 다 가능(AWS Batch·SSH)

    학습 필요성과 대용량 영상 업로드

    규칙 기반 하드코딩 플래너는 잘 되지만 바닥의 물 같은 예상 못한 경우가 있어 학습 활용 가능성이 언급됐다. 1시간 동안 찍은 360 영상을 무선으로 올리면 오래 걸린다는 문제에는, 이더넷은 느리고 불안정해 SSD를 직접 옮기는 것이 가장 빠르고 다음은 창고 같은 Wi-Fi 구역에서 자동 업로드하는 방식인데 이마저 밤새 걸렸다고 했다. Jetson Thor 내부 SSD는 그래픽카드를 떼야 해 USB SSD를 외부에 다는 안이 나왔고, NVIDIA 인코더로 압축하면 용량이 10배 이상 줄어 충전 시간 동안 올릴 수 있을지는 미확인으로 남았다.

    [12:01]이더넷으로 데이터를 전송하는 건 진짜 너무 느립니다.
    • 독에 이더넷 연결하면 빠른가? → 가능하나 매우 느림
    • 360 영상 업로드 방식(SSD 교체·Wi-Fi·압축) 미정
