Vision 60 의 연산을 Jetson Thor 로 옮기는 구조, 그 위에 올릴 클라우드

에셋을 다시 만들지 않으려면 새 구조부터 알아야 한다는 요청으로 시작했다. 회의는 Jetson Xavier 를 VCU 로, Jetson Thor 를 상위 연산으로 두는 구조를 확인하고, 클라우드 쪽은 작년 산업안전 데모 구성을 출발점으로 보는 데까지 갔다. 제조사가 열어 줄 범위, 구동시간, 데이터 업로드 방식은 열린 채 끝났다.

이 회의가 정한 것

  • 역할 분담 — Jetson Xavier 는 VCU, Jetson Thor 는 관제·주행 플래닝·매핑을 맡고 둘은 RJ45 이더넷으로 잇는다.
  • 센서 조합 — 뎁스 카메라에 상부 카메라와 고정 LiDAR 를 더하고, LiDAR 는 Jetson Thor 에 직결한다.
  • 클라우드 출발점 — AWS IoT Greengrass·AWS IoT Core·Amazon Kinesis Video Streams 세 가지를 기억하면 되고, 데모 구성이 "딱 그 구조"라는 평가가 나왔다.
  • 다음 걸음 — 교육·워크숍 아젠다와 날짜를 뽑아 8월 말~9월 초 투입 전 세팅을 끝낸다.

열린 채 남은 것

  • 제조사 개방 범위 — Ghost Robotics 의 데이터 개방과 하위단·발 모터 접근이 가능한지 확인되지 않았다.
  • 구동시간 — 기본 3시간 이상은 추가 장비가 없을 때 기준이고, Jetson Thor 를 올린 뒤의 값은 아무도 재지 않았다.
  • 업로드 방식 — SSD 교체·Wi-Fi 자동 업로드·압축 가운데 어느 쪽으로 갈지 정하지 않았다.
  • 일정 — 교육·워크숍 날짜와 현장 방문 시점이 모두 미정이다.

새 구조는 어떻게 생겼나

오늘은 … 아키텍처를 좀 말씀을 좀 듣고 그다음에 저희 교육이 좀 빠르게 잡고 … 빠르게 잡아야 될 것 같습니다.[10:34]

질문의 뿌리는 경험이었다. 현장에 가기 전에 에셋을 만들었는데 아키텍처에 맞지 않아 못 쓰게 됐고, 같은 일을 반복하지 않으려면 구조 정보를 빨리 받아야 했다. 답은 자율주행·로보틱스의 일반 구조를 따랐다. Vision 60 에 내장된 Jetson Xavier 가 하위단에서 VCU 역할로 액추에이터 제어와 통신을 맡고, 새로 올리는 Jetson Thor 가 관제·주행 플래닝·매핑 같은 상위 연산을 맡는다. 둘은 Vision 60 에서 나오는 RJ45 커넥터로 이더넷 통신을 한다.

곧바로 전력 질문이 따라왔다. Jetson Thor 를 올리면 전력 분배와 배터리 소모, 곧 구동시간이 달라진다는 우려에, 기본 3시간 이상을 보고 있지만 그것은 추가 장비가 없을 때이고, Jetson Thor 에 YOLO 객체 탐지 전용 연산 장치를 함께 올려 전력을 줄이려 한다는 답이 나왔다.

센서 배치에서 구조가 한 번 더 바뀌었다. 기존 카메라와 뎁스 카메라는 Jetson Xavier 쪽에 붙어 있어 YOLO 를 Jetson Thor 에서 돌리면 카메라 데이터를 다시 올려야 한다. 하위단까지 손대려 했지만 접근이 다 열려 있지 않아 쉽지 않았고, 전면 뎁스 카메라 두 대는 바닥을 보고 있어 퍼셉션에 쓰기 어렵다. 그래서 상부에 카메라를 따로 달고 LiDAR 는 Jetson Thor 에 직접 연결하기로 했다. 현장에 가기 전에 기존 제품을 한 번 보고 가라는 제안도 있었다.

뎁스카메라가 아래쪽으로 보고 있습니다. 그래서 저희가 카메라를 따로 달려고 하고 있고요.[10:38]

여기서 정리된 것 뎁스 카메라 + 상부 카메라 + 고정 LiDAR 조합으로 간다. [10:40] 구동시간은 열린 채 넘어갔다.

Jetson Thor 위에서 무엇을 직접 만드나

저장 공간부터 짚었다. 1TB 를 쓰고, 다른 프로젝트에서는 내부를 열어 SSD 하나를 더 넣는 방식이며, 개발자 키트가 아니라 더 작은 모듈을 쓴다는 데 동의했다. 공식 사양을 보면 1TB NVMe 는 개발자 키트의 구성품이고 모듈은 PCIe 로 NVMe 를 연결하는 방식이라, 모듈만 쓰면 저장 장치를 따로 구성해야 한다. Wi-Fi 가 없는 옵션도 있어 열어서 손보기도 한다는 이야기가 함께 나왔다.

위치 추정은 기본 부품을 믿지 않는 쪽으로 갔다. 내장 IMU 는 시프트가 생겨 쓰지 않고 LiDAR 에 포함된 IMU 를 쓰며, FAST-LIO2 는 실제로 쓰기에는 성능이 떨어져 개량해 자체 SLAM 을 만들고 있다. 가감속 제어도 Vision 60 기본 로직 대신 직접 만든 것을 얹어야 자기 알고리즘을 올릴 수 있다고 했다. SLAM·내비게이션에 연산 자원이 얼마나 필요한지에 대한 질문에는 명확한 수치가 나오지 않았다.

보행은 나눠서 정리됐다. 평지와 경사는 추상적인 명령만 주고 로봇 본체에 맡기면 문제가 없지만, 계단을 오르며 동작을 전환할 때는 발 모터단을 직접 제어해야 한다.

계단을 올라가고 이거를 스위칭할 때는 사실은 저희가 제어할 필요가 있거든요.[11:04]

클라우드에서는 무엇을 쓰나

질문의 무게가 로봇에서 클라우드로 넘어갔다. 학습 서비스는 Amazon SageMaker AI 와 Amazon Bedrock 두 가지로 소개됐는데, RL 정책 정도만 시뮬레이션에 물려 학습한다면 Amazon SageMaker AI 는 이번엔 안 써도 된다는 의견이었다. 별도의 VLA 모델을 학습하려면 MLOps 환경이 필요하고 그때 쓰는 것이 Amazon SageMaker AI 이며, Amazon Bedrock 은 LLM 같은 모델을 서빙하는 쪽이다.

데이터를 모아 올리고 학습한 모델을 배포하는 단계에서는 AWS IoT Greengrass 와 AWS IoT Core 를, 실시간 영상에는 WebRTC·HLS 로 바로 볼 수 있는 Amazon Kinesis Video Streams 를 쓴다. 혼자 해 보면 어렵지만 워크숍 한 번이면 파이프라인이 뻔해진다며 실습을 권했다.

그 외에 다른 것들도 좀 써져 있는데 제 생각에는 그건 필수적이진 않고 세 개 정도만 기억하시면 될 것 같아요.[11:17]

단, 이 구성은 기본으로 되어 있는 것이 아니라 개발해야 하는 것이고, 네트워크가 연결돼 있어야 한다는 점이 확인됐다.

학습은 언제 클라우드로 옮기나

데모에서는 사람이 제어 명령어나 결정 트리를 미리 만들지 않고 AI 모델이 이미지를 보고 로봇 제어 메시지를 직접 만들어 보내는 것도 구현했다고 소개됐다. Isaac Sim 환경에서도 같은 통신 규약을 쓸 수 있고, ROS·Isaac Sim·통신 프로토콜을 깐 EC2 하나를 세팅해 복제하면 여러 대를 따로 세팅할 필요가 없다.

파라미터와 리워드를 한꺼번에 제어할 수 있느냐는 질문에는 둘 다 된다는 답이었다. 한꺼번에는 AWS Batch 에 Environment ID·로봇·학습 에폭 같은 파라미터를 노출해 연결된 EC2 에 일괄 적용하고, 하나씩은 복제한 인스턴스에 SSH 나 DCV 로 들어가면 된다. Slurm 같은 HPC 클러스터 도구로 직접 다룰 수도 있다. 예시 설정은 노드 두 대가 서로 다른 경험 데이터를 스토리지로 동기화해 하나의 모델을 학습하는 구조였다.

한꺼번에 확장시켜서 … 테스트를 해야 된다 했을 때 클라우드로 옮기시는 걸 추천드려요.[11:56]

클라우드는 실제 PC 에서 강화학습과 Isaac Sim 을 돌리는 것보다 느리기 때문이다. 시연을 본 뒤 데모 구성이 지금 하려는 것과 같다는 반응이 나왔고, 동시에 룰 기반으로 하드코딩한 플래너가 바닥에 물이 있는 경우 같은 예상 못 한 상황에 약하다는 고민이 꺼내졌다.

아까 그 구조가 그냥 딱 그 구조인 것 같아요.[11:56]

여기서 정리된 것 환경·알고리즘은 로컬에서 먼저 정의하고, 대규모 확장 테스트 단계에서 클라우드로 옮긴다.

1시간 분량의 360도 영상을 어떻게 올리나
