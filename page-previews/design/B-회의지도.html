1

Vision 60 구조 변경

10:33–10:40

아키텍처를 모르고 만든 에셋을 못 쓰게 된 경험이 있어, 회의는 구조부터 빨리 듣자는 요청으로 시작했다. 새 구조에서 Jetson Xavier 는 VCU로 내려가 액추에이터 제어와 기본 통신을 맡고, Jetson Thor 가 관제·주행 플래닝·매핑 같은 상위 연산을 맡는다. 두 장치는 Vision 60 의 RJ45 커넥터로 이더넷 통신한다.

전면 뎁스 카메라는 바닥을 향해 퍼셉션에 쓰기 어렵다. 그래서 상부에 카메라를 따로 달고 LiDAR 는 Jetson Thor 에 직접 붙인다. 카메라가 Jetson Xavier 에 붙어 있으면 YOLO 를 위해 데이터를 다시 넘겨야 한다는 지적도 나왔지만, 하위단 접근이 열려 있지 않아 깊이 손대지는 못했다. 구동시간은 기본 3시간 이상을 보고 있고, YOLO 전용 연산 장치를 올려 전력을 줄이려 한다.

"Jetson Xavier 는 … 약간 VCU 역할을 하는 거예요." [10:35]

제조사·공급망 상황

10:40–10:53

Ghost Robotics 가 데이터를 어느 정도 열어 준다고 했지만 실제로는 그렇지 않은 것 같다는 우려가 나왔다. 중국산을 빼고 후보를 비교 분석했을 때 Ghost Robotics 가 그나마 나았다. 국내 총판은 KRM 이 올해 4월 종료되면서 LIG Nex1 이 넘겨받았다고 설명됐다.

공식 자료로는 LIG Nex1 이 2024년 7월 Ghost Robotics 지분 60%를 인수한 사실까지 확인된다. 총판 이관 자체는 출처에서 찾지 못했다.

"Ghost Robotics 에서 데이터를 오픈을 어느 정도 해준다고 했는데 좀 아닌 것 같은 느낌이 드네요." [10:40]

3

Jetson Thor 저장·SLAM·제어

10:57–11:05

Jetson Thor 는 1TB SSD 를 쓰고, 필요하면 내부를 열어 하나를 더 넣는다. 개발자 키트가 아니라 모듈을 쓴다는 데에도 동의했다. 다만 공식 사양에서 1TB NVMe 는 개발자 키트의 구성품이고, 모듈은 PCIe 로 NVMe 를 붙이는 방식이라 저장 장치를 따로 구성해야 한다.

오도메트리는 로봇 내장 IMU 에 시프트가 생겨 LiDAR 내장 IMU 를 쓴다. FAST-LIO2 는 실사용 성능이 떨어져 자체 SLAM 을 만들고 있고, 가감속 제어도 직접 만든 로직을 Jetson Thor 에서 줘야 자체 알고리즘에 얹을 수 있다. 평지·경사 보행은 로봇 본체에 추상 명령만 주면 되지만, 계단을 오르며 동작을 전환할 때는 발 모터단 제어가 필요하다.

"FAST-LIO2 를 생각을 했었는데 … 실제 활용하기에는 … 떨어지더라고요. 그래서 저희가 따로 만들고 있습니다." [11:04]

"계단을 올라가고 이거를 스위칭할 때는 사실은 저희가 제어할 필요가 있거든요." [11:04]

4

핵심 AWS 서비스

11:16–11:18

데이터를 수집해 올리고 학습한 모델을 배포하는 단계에는 AWS IoT Greengrass 와 AWS IoT Core, 실시간 영상에는 WebRTC·HLS 로 바로 볼 수 있는 Amazon Kinesis Video Streams 가 소개됐다. 그 밖의 서비스는 필수가 아니어서 처음에는 이 세 가지로 시작하면 된다는 정리였다.

Amazon SageMaker AI 는 VLA 모델처럼 MLOps 환경이 필요한 학습용이라, RL 정책만 시뮬레이션에 물려 학습한다면 이번엔 필요 없다. Amazon Bedrock 은 LLM 서빙 서비스다. 파이프라인은 혼자 해 보기 어려우니 워크숍으로 실습하자는 제안이 나왔다.

"세 개 정도만 기억하시면 될 것 같아요." [11:17]

5

데이터 파이프라인 사례

11:29–11:36

벌크 업로드 레퍼런스는 Amazon S3 의 원시 데이터를 Amazon EKS(여러 Amazon EC2 를 묶는 쿠버네티스)로 처리해 다시 저장하고, 학습 서비스로 넘기는 구조다. 비슷한 프로젝트 경험으로는 Amazon S3 에 하이브 파티셔닝으로 L0(원시)·L1(가공)·L2를 두고, 인덱싱·메타 정보는 DynamoDB 에 넣어 L1 데이터만으로 학습하는 방식이 소개됐다. 무엇을 남기고 버릴지, 타임스탬프를 어떻게 맞출지는 직접 개발할 로직이다.

Amazon Kinesis Video Streams 는 약 4초 지연이 있지만 지난 영상을 CCTV처럼 돌려 볼 수 있다(공식 문서의 HLS 지연 3–5초와 일치). LiDAR 원시 데이터를 모두 올리는 건 너무 무거워 온프레미스가 더 빠를 수 있다는 의견도 나왔다. Isaac Lab 은 학습과 시뮬레이션을 분리해 체크포인트를 공유하며 분산 처리할 수 있고, Isaac Sim 은 AMI 로 바로 띄울 수 있다.

"비디오 데이터가 오는 90% 이상은 다 쓸모없는 데이터입니다." [11:31]

6

AWS 산업안전 데모

11:36–11:46

Unitree Go2 위 Jetson Orin 에 YOLO 를 AWS IoT Greengrass 로 배포하고(학습은 클라우드), RGB 카메라 영상은 Amazon Kinesis Video Streams 의 WebRTC 로 실시간 시청했다. CPU·메모리·배터리 메트릭과 위치는 AWS IoT Core(MQTT)로 올려 Grafana 에 띄웠고, ROS 와 연결된 커맨드 컴포넌트가 MQTT 로 클라우드의 원격 명령을 받는다. 이 구성은 네트워크 연결이 전제이고 직접 개발해야 한다.

학습 데이터가 없는 상황은 파운데이션 모델이 더 잘 추론할 수 있어, 엣지의 YOLO 로 먼저 거르고 confidence 가 낮을 때만 Amazon Bedrock 의 VLM 에 판단을 넘기는 구성이 제안됐다. 비용은 IoT 서비스가 가장 싸고 Amazon Bedrock 은 토큰 기반이다.

"confidence 값이 나올 거잖아요. 그게 너무 낮다 하면은 이제 여기 추론을 보내는 형태로 저는 할 것 같아요." [11:45]

7

Isaac Sim 클라우드 학습

11:46–11:57

AI 모델이 로봇이 보는 이미지를 판단해 제어 메시지를 직접 만들어 보내는 구현도 소개됐다. Isaac Sim 환경은 Amazon EC2 하나에 ROS·Isaac Sim·통신 프로토콜을 세팅한 뒤 복제해 쓴다. 한꺼번에 바꾸려면 AWS Batch 에 Environment ID·로봇·학습 에폭 같은 파라미터를 노출해 일괄 제어하고, 하나씩은 SSH·DCV 로, 대규모는 Slurm 으로도 다룰 수 있다. 노드 수를 정하면 여러 노드의 경험 데이터를 스토리지로 동기화해 하나의 모델을 학습한다.

다만 클라우드는 로컬 PC 보다 느리다. 로컬에서 환경·알고리즘을 먼저 정한 뒤 확장 테스트 단계에서 옮기라는 권고였다. 데모 구조가 "딱 그 구조"라는 평가와 함께, 하드코딩한 룰 기반 플래너가 바닥에 물이 있는 경우 같은 예외 상황에 약하다는 이야기가 나왔다.

"한꺼번에 확장시켜서 … 테스트를 해야 된다 했을 때 이제 클라우드로 옮기시는 걸 추천드려요." [11:56]

8

대용량 데이터 업로드

11:59–12:03

1시간 동안 찍은 360도 영상을 무선으로 올리는 데 시간이 매우 오래 걸렸다. 도킹해 이더넷으로 옮기는 것은 가능하지만 이더넷이 느리고 불안정하다. 가장 빠른 건 SSD 물리 교체인데, Jetson Thor 는 SSD 를 꽂으려면 그래픽카드를 먼저 떼야 해 사람이 붙어야 한다.

USB SSD 를 밖으로 빼는 방법, 창고처럼 특정 Wi-Fi 에 붙으면 자동으로 올리는 방법(그래도 밤새 걸렸다), NVIDIA 인코더로 압축하는 방법이 거론됐다. 압축 여부에 따라 10배 이상 차이가 난다는 말이 있었지만, 이 수치는 출처에 없고 코덱·비트레이트에 따라 달라진다.

"스토리지 자체로 … 받아와가지고 옮기는 게 제일 빠르긴 해요." [12:00]

"로봇은 현장에 자주 가면 좋습니다." [12:17]

SK 입장에서 건설 산업의 첫 사례이니 3사가 함께 레퍼런스를 만들어 외부에 공유·발표하고, Seoul Dynamics 도 파트너로 함께 보여주자는 구상이 공유됐다.

"그냥 메일 주세요." [12:22]

분석 메모 — 지도에서 읽히는 것 (추정 포함)

추정데모 구성이 사실상 설계 초안이다. 데모는 Jetson Orin 위 YOLO 를 AWS IoT Greengrass 로 배포하고 영상·메트릭·원격 명령을 클라우드로 처리했다. 새 구조는 데모의 Jetson Orin 자리를 Jetson Thor 로 바꾸는 데서 시작하는 편이 빠르다. 6 · 7

추정룰 기반 플래너의 예외 상황과 VLM 보완 구성이 맞물린다. 바닥 물 같은 예상 못 한 상황에 낮은 confidence 경로를 쓸 수 있다. 다만 클라우드 왕복 지연이 있어 주행 판단이 아니라 상황 판단에만 맞다. 6 · 7

SSD 물리 교체는 현장에서 매번 하기 어려울 수 있다. Jetson Thor 모듈은 저장 장치를 따로 구성해야 하고, 꽂으려면 그래픽카드를 떼야 한다. 3 · 8

추정구동시간이 줄면 업로드 계획이 함께 흔들린다. 3시간 이상은 추가 장비 없는 기준이고, Jetson Thor 소비 전력은 40–130 W 다. 1시간 단위 수집과 충전 중 업로드가 모두 구동시간에 묶여 있다. 1 · 8

추정교육 일정이 세팅보다 늦으면 에셋을 다시 만드는 일이 되풀이될 수 있다. 조기 신호는 아젠다·날짜 회신 지연이다. 1 · 10

권장 후속 조치 — 담당·기한은 모두 미정.

제조사에 발 모터 제어·가감속 제어 교체·카메라 하위 접근 범위를 서면으로 확인한다(LIG Nex1 경로 활용 가능).

Jetson Thor 캐리어 보드의 저장 구성과, 분해 없이 데이터를 꺼내는 방식(외부 USB SSD 안 포함)을 함께 정한다.

8월 중순 수동 운용 전에 장비를 모두 단 상태의 구동시간과 NVENC 압축 시 360도 영상 1시간 분량을 잰다.

VLM 후보는 크랙·바닥 물 같은 현장 이미지로 정확도와 응답 지연을 함께 본다.
