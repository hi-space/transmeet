비전 유통 아키텍처 변경 방안 논의

2026-07-27 10:33–12:24, 1시간 50분

Vision 60은 Jetson Thor가 상위 연산을 맡고 Jetson Xavier가 VCU로 남는 구조로 바꾸고, 클라우드는 AWS IoT Greengrass·AWS IoT Core·Amazon Kinesis Video Streams 세 서비스 중심으로 구성합니다.

센서 배치 방향을 정했습니다. 자체 SLAM과 자체 가감속 제어도 쓰기로 했습니다. 목표는 8월 말~9월 초 현장 투입 전까지 교육과 워크숍으로 세팅을 끝내는 것입니다. 다만 Ghost Robotics의 저수준 제어 개방 범위, 장비 장착 후 구동시간, 대용량 데이터 회수 방법, 교육 날짜는 아직 정하지 못했습니다.

요점

  1. ①

    Jetson Xavier는 VCU 역할로 유지

    Vision 60에 내장된 Jetson Xavier는 액추에이터 제어와 기본 통신만 맡습니다. Jetson Thor가 보내는 제어 명령을 받아 실행합니다. 기존 내장 센서와 모터는 그대로 Jetson Xavier에 연결되어 있습니다. 내장 컴퓨터 사양은 공식 자료의 Jetson Xavier(32GB RAM, 2TB NVMe SSD)와 일치합니다.

  2. ②

    Jetson Thor가 상위 연산 담당

    관제, 주행 플래닝, 매핑, YOLO 추론은 Jetson Thor가 맡습니다. Jetson Xavier와는 Vision 60에서 나오는 RJ45 커넥터로 이더넷 통신을 합니다. Jetson Xavier에 붙은 카메라 데이터도 이 링크로 Jetson Thor에 넘겨야 합니다. 이 링크의 대역폭과 지연은 아직 검토하지 않았습니다(추정 리스크).

  3. ③

    LiDAR와 상부 카메라 추가

    LiDAR는 Jetson Thor에 직접 연결합니다. 내장 뎁스 카메라와 전면 광각 카메라는 바닥을 향해 퍼셉션에 쓰기 어렵습니다. 그래서 상부에 퍼셉션용 카메라를 따로 답니다. 기존 카메라는 하위단 접근이 열려 있지 않아 깊이 활용하지 못합니다.

  4. ④

    발 모터 제어 접근 범위 미확인

    평지와 경사에서는 로봇 본체에 전진·회전 같은 추상 명령만 주면 충분합니다. 계단 오르기로 동작을 전환할 때는 발 모터단을 직접 제어해야 합니다. Ghost Robotics가 이 수준까지 열어 줄지는 아직 모릅니다.

  5. ⑤

    장비 추가 후 구동시간 미측정

    Vision 60의 기본 구동시간은 3시간 이상입니다. 이 값은 추가 장비가 없을 때 기준입니다. Jetson Thor의 소비 전력은 공식 사양상 40–130 W입니다. 전력 소모를 줄이려고 YOLO 전용 연산 장치를 올릴 계획입니다. 하지만 장착 후 구동시간은 재지 않았습니다.

  6. ⑥

    핵심 AWS 서비스 세 가지

    데이터 수집과 모델 배포는 AWS IoT Greengrass와 AWS IoT Core가 맡습니다. 실시간 영상은 Amazon Kinesis Video Streams가 맡습니다. RL 정책만 학습한다면 Amazon SageMaker AI는 이번에 쓰지 않아도 됩니다. 실시간 관제는 현장 네트워크 연결이 전제입니다. 관제 기능은 직접 개발해야 합니다.

  7. ⑦

    신뢰도 낮은 판단만 Amazon Bedrock VLM으로

    엣지에서 YOLO와 결정 트리로 먼저 판단합니다. confidence가 낮을 때만 Amazon Bedrock의 VLM에 판단을 요청합니다. 모든 판단을 보내지 않는 이유는 클라우드 왕복과 추론에 시간이 걸리기 때문입니다. 어떤 모델이 가장 정확한지는 테스트 후 고릅니다.

  8. ⑧

    대용량 데이터 회수 방법 미정

    1시간 동안 찍은 360도 영상을 무선으로 올리면 시간이 매우 오래 걸립니다. SSD 물리 교체가 가장 빠릅니다. 하지만 Jetson Thor는 SSD 위의 그래픽카드를 먼저 떼야 합니다. Wi-Fi 자동 업로드와 NVIDIA 인코더 압축도 후보입니다. 어느 방식으로 할지는 정하지 않았습니다.

  9. ⑨

    Isaac Sim·Isaac Lab 클라우드 학습

    Isaac Sim이 설치된 AMI로 Amazon EC2 인스턴스를 바로 띄웁니다. 인스턴스 하나를 세팅해 복제한 뒤 AWS Batch로 학습 파라미터를 한꺼번에 제어합니다. 클라우드 학습은 로컬 PC보다 느립니다. 그래서 환경과 알고리즘은 로컬에서 먼저 정의하고, 대규모 확장 테스트 단계에서 클라우드로 옮깁니다.

흐름

1Jetson Thor가 상위 연산, Jetson Xavier가 VCU 담당

Vision 60은 기존 내장 방식 그대로 쓰지 않고 Jetson Thor 중심 구조로 바꿉니다. 현장 방문 전에 만든 에셋이 아키텍처와 맞지 않아 못 쓰게 된 일이 있었습니다. 그래서 아키텍처를 먼저 확정하고 교육 방향을 빨리 잡기로 했습니다. 구조는 대부분의 자율주행·로보틱스 시스템처럼 하위 제어 유닛과 상위 인지·플래닝 층으로 나눕니다.

Vision 60에 내장된 Jetson Xavier는 VCU로서 액추에이터 제어와 통신을 맡습니다. Jetson Thor는 관제, 주행 플래닝, 매핑을 맡고 Jetson Xavier에 제어 명령을 내립니다. 두 장치는 Vision 60의 RJ45 커넥터로 이더넷 통신을 합니다. 기존 내장 카메라는 바닥을 향해 퍼셉션에 부족하므로 상부에 카메라를 따로 달고, LiDAR는 Jetson Thor에 직접 연결합니다. 장비가 늘어 구동시간이 3시간 이상 기준보다 줄어들 수 있습니다.

  • 내장 카메라 — 전면 뎁스 카메라 2대와 광각 카메라 2대 모두 바닥 방향
  • 센서 조합 — 뎁스 카메라 + 상부 카메라 + 고정 LiDAR
  • 카메라 데이터 — Jetson Thor에서 YOLO를 돌리려면 Jetson Xavier 쪽 카메라 데이터를 이더넷으로 다시 전달 필요
  • 전력 — YOLO 전용 연산 장치를 Jetson Thor 쪽에 올려 전력 절감 계획(장치 명칭 미확인)
  • 공식 사양 — 기본 센서 RGB 카메라 5대·D435 뎁스 센서 4대, 연속 보행 3시간 이상. 카메라 장착 방향은 사양에 미기재
  • 권고 — 투입 전 기존 Vision 60 실물을 한 번 직접 확인

2Ghost Robotics 데이터 개방은 기대보다 제한적

Vision 60은 중국산을 제외한다는 요구 조건으로 고른 플랫폼입니다. Rainbow, Spot 등 후보를 비교한 결과 Ghost Robotics가 가장 나았습니다. 하지만 Ghost Robotics가 약속한 데이터 개방은 실제로는 제한적이라는 우려가 있습니다. 하위단 접근이 막히면 카메라 활용과 발 모터 제어에 영향이 있습니다.

국내 총판은 KRM이었으나 올해 4월 종료되었고 LIG Nex1이 넘겨받았습니다. 이 이관 사실은 공식 자료로 확인하지 못했습니다. LIG Nex1은 2024년 7월 Ghost Robotics 지분 60%를 인수했습니다. 프로젝트는 LIG Nex1과 직접 연락하고 있으며, 방법이 없지는 않다는 답을 받았습니다. 데이터 개방 수준과 하위단 접근 가능 여부는 아직 모릅니다.

  • 선정 기준 — 중국산 제외
  • 비교 후보 — Rainbow, Spot 등 비교 후 Ghost Robotics 선택
  • 인수 — LIG Nex1이 2024년 7월 Ghost Robotics 지분 60%를 2억 4천만 달러에 인수(공식 보도자료)
  • 총판 — KRM 올해 4월 종료 후 LIG Nex1로 이관, 공식 자료 미확인
  • 협력사 — Seoul Dynamics는 건설 로봇(지게차 로봇) 경험 보유

3오도메트리는 LiDAR 내장 IMU, SLAM·가감속 제어는 자체 개발

Vision 60 내장 IMU는 시프트가 생겨 오도메트리를 만들기 어렵습니다. 그래서 LiDAR에 포함된 IMU로 오도메트리를 구성합니다. 뎁스 카메라에도 IMU가 있지만 LiDAR와 센서 퓨전을 하는 부담이 큽니다. SLAM은 FAST-LIO2를 검토했으나 실사용 성능이 부족해 다층·3D 구조에 맞게 개량한 자체 SLAM을 개발하고 있습니다.

가감속 제어도 Vision 60 기본 로직 대신 Jetson Thor에서 직접 만든 로직을 씁니다. 그래야 자체 알고리즘에 얹을 수 있고, Vision 60은 기본 제어만 맡습니다. 평지와 경사에서는 로봇 본체에 추상 명령만 주면 됩니다. 계단 오르기로 전환할 때는 발 모터단 제어가 필요하지만 접근 범위는 미확인입니다. Jetson Thor는 개발자 키트가 아닌 모듈을 쓰므로 저장 장치를 따로 구성해야 합니다.

  • 3D LiDAR — 보통 IMU 내장, 센서 퓨전에 유리
  • SLAM 자원 — SLAM·내비게이션 모델의 Jetson Thor 자원 사용량 미정, 파라미터가 커지면 부담
  • 저장 장치 — 1TB SSD 사용, 다른 프로젝트에서는 내부를 열어 1TB 추가 장착
  • 모듈 사양 — 공식 사양상 1TB NVMe는 개발자 키트 구성품, 모듈은 PCIe로 NVMe 연결 후 캐리어 보드 구성 필요
  • 통신 — Jetson Thor 자체 통신 가능, 옵션별로 Wi-Fi가 없으면 열어서 대응

4핵심 AWS 서비스 세 가지와 Amazon S3 L0/L1/L2 데이터 계층

AWS 모델 학습 서비스는 Amazon SageMaker AI와 Amazon Bedrock 두 가지입니다. 이번 프로젝트는 RL 정책을 시뮬레이션에 연결해 학습하는 정도라 Amazon SageMaker AI가 필요 없습니다. Amazon SageMaker AI는 VLA 모델 학습처럼 MLOps 환경이 필요할 때 씁니다. 핵심은 데이터 수집·업로드와 모델 배포 단계이며, AWS IoT Greengrass와 AWS IoT Core가 이 단계를 맡습니다. 실시간 영상은 Amazon Kinesis Video Streams로 WebRTC나 HLS 방식으로 봅니다.

데이터는 Amazon S3에 L0(원시), L1(가공), L2 계층으로 하이브 파티셔닝을 적용해 저장합니다. Amazon EKS가 여러 Amazon EC2 인스턴스로 원시 데이터를 빠르게 처리해 L1에 다시 저장합니다. 비디오 데이터의 90% 이상은 쓸모가 없어 세그먼트와 큐레이션이 필요합니다. 어떤 데이터를 남기고 버릴지, 타임스탬프를 어떻게 맞출지는 직접 개발해야 합니다. 다만 LiDAR 원시 데이터는 너무 무거워 클라우드 업로드보다 온프레미스 처리가 더 빠릅니다.

  • 메타 인덱스 — 구간·인덱싱 정보는 DynamoDB에 저장, L1 데이터로 바로 학습
  • 개발 차이 — 데이터 선택·정렬 로직은 지금과 같고, 저장 위치만 PC SSD에서 클라우드 스토리지로 변경
  • Wirobotics 사례 — AWS IoT Core로 MQTT 데이터, Amazon Kinesis Video Streams로 영상 수집, 중간 가공은 직접 작성한 코드로 처리
  • Neubility 사례 — 이동 로봇의 실시간 영상 업로드 레퍼런스
  • 영상 지연 — 약 4초 지연, 지난 영상을 CCTV나 rosbag처럼 재생 가능(공식 문서상 HLS 지연 보통 3–5초)
  • 실습 — AWS IoT Greengrass·AWS IoT Core 파이프라인은 혼자 익히기 어려워 워크숍으로 실습

5산업안전 데모 구성 재사용, 낮은 신뢰도만 Amazon Bedrock VLM으로

AWS가 작년 부스에서 선보인 산업안전 데모는 이 프로젝트와 구조가 거의 같습니다. Unitree Go2가 공장을 돌며 위험 현장이나 쓰러진 사람을 감지하고 리포트를 보냅니다. YOLO 모델은 클라우드에서 학습하고 AWS IoT Greengrass로 Jetson Orin에 배포했습니다. 영상은 Amazon Kinesis Video Streams(WebRTC)로 실시간 재생합니다. ROS 명령 컴포넌트가 AWS IoT Core와 MQTT로 연결되어 클라우드에서 원격 제어를 합니다.

YOLO로 잡지 못하는 상황은 영상·위치·메트릭을 묶어 VLM에 판단을 맡깁니다. 단순한 크랙은 YOLO로 충분하고, 학습 데이터가 없는 상황은 파운데이션 모델이 더 잘 판단합니다. 엣지에서 YOLO와 결정 트리로 먼저 거르고 confidence가 낮을 때만 Amazon Bedrock에 추론을 요청합니다. 클라우드 왕복과 추론에 시간이 걸리기 때문입니다. 이 구성은 기성품이 아니라 직접 개발해야 합니다. 실시간으로 동작하므로 네트워크 연결이 전제입니다.

  • Grafana — MQTT로 올라온 Jetson Orin의 CPU·메모리·배터리, 이벤트 감지 횟수, 로그·에러, 실시간 위치 시각화
  • 배터리 관리 — 잔여 배터리가 부족하면 충전 위치로 복귀 판단
  • 리포트 — 에이전트 AI가 위험 수준·권고 사항·근거 영상을 담은 순찰 보고서 생성
  • 비용 — IoT 서비스가 가장 저렴, Amazon Bedrock은 토큰 기반 과금이며 예상보다 저렴
  • 모델 선택 — 현장 전용 파운데이션 모델은 사실상 부재. Anthropic·OpenAI·NVIDIA 등 Amazon Bedrock 모델 중 테스트 후 선정
  • AI 직접 제어 — 데모에서 AI 모델이 이미지를 보고 로봇 제어 메시지를 직접 생성하는 방식도 구현

6Isaac Sim·Isaac Lab은 Amazon EC2 하나를 복제해 AWS Batch로 일괄 제어

Isaac Sim 시뮬레이션 환경도 실제 로봇과 같은 통신 규약으로 이 시스템 안에 구현할 수 있습니다. Isaac Sim이 설치된 AMI로 Amazon EC2 인스턴스를 띄우고 ROS, Isaac Sim, 통신 프로토콜을 한 번 세팅합니다. 세팅한 인스턴스는 복제해서 그대로 씁니다. AWS Batch에 Isaac Lab Environment ID, 로봇, 학습 에폭 같은 파라미터를 노출하면 연결된 여러 인스턴스를 한꺼번에 설정합니다. 여러 노드의 경험 데이터는 공유 스토리지로 동기화해 하나의 모델을 함께 학습합니다.

개별 인스턴스는 SSH나 DCV(원격 GUI)로 접속해 따로 제어할 수 있습니다. 학습 로그는 클라우드에서 확인하고, 학습한 정책은 Isaac Sim에서 바로 돌려 봅니다. 다만 클라우드 학습은 로컬 PC보다 느립니다. 환경·알고리즘·보상은 로컬에서 먼저 정의하고, 대규모 확장 테스트 단계에서 클라우드로 옮깁니다.

  • AWS Batch 파라미터 — 노드 수(노드 2개 = PC 2대), 노드당 GPU 수, 이터레이션, 태스크 값, 시작 시 실행 명령
  • 분산 학습 — 공식 블로그상 AWS Batch 다중 노드 병렬 작업, 체크포인트는 Amazon EFS에 저장
  • 접속 포트 — SSH TCP 22, DCV TCP 8443
  • 대안 — 대규모 Amazon EC2 제어에 Slurm 같은 HPC 스케줄러 사용 가능
  • 비용 — Isaac Sim AMI는 무료, g6e·g7e 등 Amazon EC2 인프라 비용 별도
  • 남은 고민 — 보상 설계, 학습 시작 방식, 환경 세팅 방식 미정

7360도 영상 회수는 SSD 교체가 가장 빠르나 방식 미정

1시간 동안 움직이며 찍은 360도 영상은 무선 업로드에 매우 오랜 시간이 걸립니다. 저장 장치를 물리적으로 꺼내 옮기는 방법이 가장 빠르지만 사람이 개입해야 합니다. Jetson Thor에 꽂은 SSD를 빼려면 위의 그래픽카드를 먼저 떼야 합니다. 기존에 SSD를 추가한 목적도 회수가 아니라 저장 용량 확장이었습니다.

특정 Wi-Fi에 붙으면 자동으로 올리는 방법도 있지만 밤새 걸린 경험이 있습니다. 도킹 스테이션과 로봇을 이더넷으로 연결하는 방법은 가능하지만, 로봇 이더넷은 느리고 불안정해 거의 쓰지 않습니다. NVIDIA 인코더로 압축하면 용량이 크게 줄어듭니다. 카메라 데이터는 포인트 이미지 촬영이나 타임랩스 촬영으로 용량을 줄이는 방안도 고려합니다. 어느 방식으로 회수할지는 아직 정하지 않았습니다.

  • 외부 USB SSD — 외부 USB SSD를 달고 로직으로 데이터를 빼내는 방안, 구성 미검토
  • 압축률 — 10배 이상 압축이라는 수치는 공식 자료 미확인. 압축률은 코덱·비트레이트에 따라 차이
  • Jetson Thor 인코딩 — 2026년 1월부터 NVIDIA Video Codec SDK가 Jetson Thor 지원
  • 운용 제약 — 충전 시간 동안 업로드 완료를 기다려야 하는 구조

88월 중순 수동 운용, 8월 말~9월 초 투입 전 세팅 완료 목표

현장은 두 차례 나눠 방문하는 것을 기본으로 하고 용인을 우선 검토합니다. 울산은 시험장으로 쓰기 어렵습니다. 현장 방문은 하루 종일 걸립니다. 시뮬레이션만으로는 튜닝에 한계가 있어 로봇은 현장에 자주 갈수록 좋습니다. 처음에는 자율주행이 아닌 수동 운용으로 8월 중순 정도부터 투입할 수 있습니다.

기초 교육은 집중도가 떨어지므로 필요한 내용만 담은 교육 아젠다를 짜고 가능한 날짜를 빠르게 제안합니다. 워크숍 형식과 일정도 함께 제안합니다. 8월 말~9월 초 투입 전까지 세팅을 끝내고 이후 Q&A 세션으로 이어 가기로 했습니다. 궁금한 점은 메일 루프로 보내면 전문가 네 명 중 한 명이 답하고 에셋을 공유합니다. 이번 지원은 파트너 지원이 아니라 AWS 고객 지원 프로그램으로 진행합니다.

  • 현장 자료 — 용인 현장 실측, 관련 데이터 제공, 플랜트 LiDAR 스캐닝 데이터 제공
  • 현재 로봇 — 다른 프로젝트용이라 서 있는 상태 정도만 확인 가능
  • 공동 레퍼런스 — SK의 첫 건설 산업 사례로 외부 공유·발표, Seoul Dynamics를 파트너로 소개
  • 건축 법규 — 데이터 센터 건축은 설계·시공 분리 법규 때문에 설계 역할 제한
  • 일정 위험 — 워크숍이 세팅보다 늦으면 에셋 재작업 위험(추정)

산업안전 데모 구성 재사용

데모는 Jetson Orin 위 YOLO를 AWS IoT Greengrass로 배포하고, 영상은 Amazon Kinesis Video Streams, 메트릭과 원격 명령은 AWS IoT Core와 Grafana로 처리합니다. 이 구성은 프로젝트의 센서·로봇 구조와 거의 같습니다. 추정: Jetson Orin 자리에 Jetson Thor를 넣는 방식으로 시작하면 처음부터 새로 구성하는 것보다 빠릅니다.

룰 기반 하드코딩 플래너는 잘 돌지만 바닥에 물이 있는 경우처럼 예상하지 못한 상황에 약합니다. 추정: confidence가 낮을 때만 Amazon Bedrock VLM에 넘기는 구성이 이 약점을 보완합니다. 추정: 클라우드 왕복 지연 때문에 주행 판단에는 맞지 않고 상황 판단에만 적합합니다.
