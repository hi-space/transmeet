2026-07-27 10:33–12:24

  • 핵심 AWS 서비스 세 가지 — 데이터 수집·모델 배포에는 AWS IoT Greengrass·AWS IoT Core, 실시간 영상에는 Amazon Kinesis Video Streams 를 쓰고, RL 정책만 학습한다면 Amazon SageMaker AI 는 이번에 쓰지 않아도 된다는 안내

회의 요약

배경·목적

  • Vision 60 연산 구조 변경 — 기존 Jetson Xavier 중심 구조를 Jetson Thor 중심으로 바꾸는 아키텍처를 듣고, 교육·방향을 빨리 잡기 위한 자리였다.
  • 잘못 만든 에셋 재발 방지 — 아키텍처를 모르고 만든 에셋을 못 쓰게 된 경험이 있어 아키텍처 정보를 빨리 받아야 한다는 요청이 나왔다.
  • AWS 측 클라우드 구성 소개 — 로봇 데이터 수집·학습·배포·시뮬레이션에 쓸 AWS 서비스와 레퍼런스 아키텍처, 산업안전 데모가 함께 공유됐다.

주요 논의

  • Xavier 는 VCU, Thor 는 상위 연산 — Xavier 가 액추에이터 제어·통신을 맡고, Thor 가 관제·주행 플래닝·매핑을 맡으며 둘은 RJ45 이더넷으로 연결된다.
  • 배터리 구동시간 우려 — Thor 추가로 전력 분배와 구동시간이 달라질 수 있다는 질문에, 기본 3시간 이상을 보고 있고 YOLO 전용 연산 장치를 올려 전력을 줄이려 한다는 답이 나왔다.
  • 센서 배치 — 내장 뎁스 카메라 두 개가 바닥을 향해 퍼셉션에 부족하므로 상부에 별도 카메라를 달고, LiDAR 는 Thor 에 직접 연결하기로 구상했다.
  • Ghost Robotics 데이터 개방 의문 — 데이터를 어느 정도 열어 준다고 했지만 실제로는 아닌 것 같다는 의견이 나왔고, 국내 총판은 KRM 이 올해 4월 종료돼 LIG Nex1 이 넘겨받았다고 설명됐다.
  • 오도메트리·SLAM 자체 개발 — 내장 IMU 는 시프트가 생겨 LiDAR 내장 IMU 를 쓰고, FAST-LIO2 는 실사용 성능이 떨어져 자체 SLAM 과 가감속 제어 로직을 만들고 있다.
  • 보행 제어 범위 — 평지·경사는 로봇 본체에 맡기면 되지만, 계단 오르기 전환 시에는 발 모터단 제어가 필요하다는 의견이 나왔다.
  • 핵심 AWS 서비스는 세 가지 — 데이터 수집·모델 배포용 AWS IoT Greengrass·AWS IoT Core 와 실시간 영상용 Amazon Kinesis Video Streams 를 기억하면 되고, RL 정책만 학습하면 Amazon SageMaker AI 는 이번엔 불필요하다고 정리됐다.
  • 데이터 레이크 구성 — S3 에 하이브 파티셔닝으로 L0(원시)·L1(가공)·L2 를 두고 EKS 로 처리, DynamoDB 에 메타 정보를 넣는 방식이 소개됐으며 비디오 데이터의 90% 이상은 쓸모없다는 경험이 공유됐다.
  • LiDAR 원시 데이터 업로드는 비효율 — 데이터가 너무 무거워 온프레미스 처리가 더 빠를 수 있다는 의견이 나왔다.
  • 산업안전 데모 — Unitree Go2 + Jetson Orin 에 YOLO 를 IoT Greengrass 로 배포하고, Kinesis Video Streams·IoT Core(MQTT)·Grafana 로 영상·메트릭·원격 제어를 구현했으며, 이는 네트워크 연결 전제이고 직접 개발이 필요하다.
  • YOLO 우선, 낮은 신뢰도만 VLM — 엣지에서 YOLO·결정 트리로 거르고 confidence 가 낮을 때만 Amazon Bedrock 의 VLM 으로 보내는 방식이 제안됐고, 비용은 IoT 서비스가 가장 싸며 Bedrock 은 토큰 기반이다.
  • Isaac Sim/Lab 클라우드 학습 — AMI 로 환경을 띄우고 EC2 하나를 세팅해 복제하며, AWS Batch 로 환경 ID·로봇·에폭 등 파라미터를 일괄 제어하거나 SSH·DCV·Slurm 으로 개별 제어할 수 있다.
  • 클라우드 학습은 로컬보다 느림 — 로컬 PC 에서 환경·알고리즘을 먼저 정의한 뒤 대규모 확장 테스트 시 클라우드로 옮기라는 권고가 나왔다.
  • 대용량 영상 업로드 — 1시간 360도 영상 업로드가 매우 오래 걸렸고, 이더넷은 느리고 불안정해 SSD 물리 교체가 가장 빠르며, 차선책은 특정 Wi-Fi 접속 시 자동 업로드(밤새 걸림)와 NVIDIA 인코더 압축(10배 이상 차이)이다.

합의·결정

  • LiDAR 는 Thor 직결, 별도 전면 카메라 추가 — 뎁스 카메라 + 상부 카메라 + 고정 LiDAR 조합으로 가는 방향이 정리됐다.
  • 현장 방문은 잦을수록 좋다 — 시뮬레이션만으로는 튜닝 한계가 있어 실측 데이터와 함께 가야 한다는 데 공감했고, 8월 중순 정도부터 수동 운용 형태로 투입 가능하다는 언급이 있었다.
  • 교육·워크숍 아젠다를 AWS 측이 작성 — 기초 교육 대신 포커스된 아젠다와 워크숍 일정을 뽑아, 8월 말~9월 초 투입 전까지 세팅을 끝내고 이후 Q&A 세션으로 이어가기로 했다.
  • 문의는 메일 루프로 — 지원 요청은 망설이지 말고 메일로 보내면 전문가 네 명 중 한 명이 답하고 에셋을 공유하기로 했다.
  • 이번 지원은 고객 지원 프로그램 — AWS 팀은 원래 파트너를 직접 지원하지 않으며, 이번 건은 고객을 지원하는 프로그램으로 이해해 달라는 점이 강조됐다.

Vision 60 구조 변경

10:33–10:40

요지

Vision 60 를 Jetson Thor 중심으로 바꾸려면 아키텍처를 먼저 알아야 에셋을 다시 만드는 일이 없다는 문제의식에서 논의가 시작됐다. 일반적인 자율주행·로보틱스 구조처럼 Jetson Xavier 는 VCU 로 액추에이터 제어와 기본 통신을 맡고, Jetson Thor 가 관제·주행 플래닝·매핑 같은 상위 연산을 맡으며, 둘은 Vision 60 의 RJ45 커넥터를 통한 이더넷으로 연결된다. 전력 분배가 달라져 구동시간이 줄 수 있다는 우려에는 기본 3시간 이상을 보고 있고, YOLO 객체 탐지 전용 연산 장치를 Jetson Thor 에 올려 전력을 줄이려 한다는 답이 나왔다. 기존 카메라·뎁스 카메라와 통신은 Jetson Xavier 에, LiDAR 같은 센서는 Jetson Thor 에 직접 붙이는데, 전면 광각 카메라 두 대와 뎁스 카메라가 바닥만 보고 내부 배선을 열 수도 없어 Jetson Thor 쪽에 퍼셉션용 상부 카메라를 따로 달아 뎁스 카메라·상부 카메라·고정 LiDAR 조합으로 가기로 했다.

Jetson Thor 저장·SLAM·제어

10:57–11:05
