Vision 60 아키텍처 변경 방안 논의

2026년 7월 27일 10:33–12:24 (1시간 50분)

Vision 60은 Jetson Xavier가 하위 제어(VCU)를 맡고, 새로 올리는 Jetson Thor가 퍼셉션·플래닝·매핑·관제를 맡는 구조로 바꿉니다.

클라우드 연동은 AWS IoT Greengrass, AWS IoT Core, Amazon Kinesis Video Streams 세 서비스로 시작합니다. 제조사의 저수준 제어 개방 범위, 대용량 데이터 업로드 방식, 교육 일정은 아직 정하지 못했습니다.

요점

  1. 1

    Jetson Xavier는 VCU, Jetson Thor는 상위 연산

    Jetson Xavier는 액추에이터 제어와 기본 통신만 맡고 Jetson Thor의 제어 명령을 받습니다. 두 장치는 Vision 60의 RJ45 단자로 이더넷 통신합니다. 센서 데이터와 제어 명령이 같은 링크로 오가는데, 그 대역폭은 아직 검토하지 않았습니다(추정).

  2. 2

    LiDAR 직결과 상부 카메라 추가

    내장 뎁스 카메라가 바닥을 향해 있어 퍼셉션에 쓰기 어렵습니다. 상부에 별도 카메라를 달고, 고정 LiDAR는 Jetson Thor에 직접 연결합니다. 오도메트리는 시프트가 생기는 내장 IMU 대신 LiDAR 내장 IMU로 계산합니다.

  3. 3

    제조사 저수준 제어 개방 범위

    평지와 경사는 로봇 본체 제어에 맡기면 됩니다. 계단 동작을 바꿀 때는 발 모터 제어가 필요하고, 가감속 제어도 직접 만든 로직으로 바꾸려 합니다. Ghost Robotics가 이 제어를 열어 줄지는 아직 모릅니다.

  4. 4

    핵심 클라우드 서비스 세 가지

    데이터 수집과 모델 배포에는 AWS IoT Greengrass와 AWS IoT Core를, 실시간 영상에는 Amazon Kinesis Video Streams를 씁니다. RL 정책만 학습한다면 Amazon SageMaker AI는 이번에 쓰지 않아도 됩니다. 파이프라인 구성은 워크숍에서 실습합니다.

  5. 5

    YOLO 우선, 낮은 신뢰도만 VLM

    엣지에서 YOLO와 결정 트리로 대부분의 장면을 거릅니다. confidence가 낮을 때만 Amazon Bedrock의 VLM에 판단을 보냅니다. 어떤 파운데이션 모델을 쓸지는 현장 영상으로 테스트한 뒤 정합니다.

  6. 6

    대용량 데이터 업로드 방식 미정

    1시간 분량의 360도 영상은 무선으로 올리는 데 매우 오래 걸립니다. 이더넷은 느리고 불안정해서 SSD를 직접 교체하는 방법이 가장 빠릅니다. 특정 Wi-Fi 자동 업로드와 NVIDIA 인코더 압축이 대안이지만 기본 방식은 정하지 않았습니다.

  7. 7

    Isaac Sim·Isaac Lab 클라우드 학습

    AMI로 Isaac Sim 환경을 띄우고 Amazon EC2 한 대를 세팅해 복제합니다. AWS Batch로 파라미터를 한꺼번에 제어하거나 SSH·DCV로 한 대씩 제어합니다. 클라우드는 로컬보다 느려서 대규모 확장 테스트 단계에서 옮기는 것을 권합니다.

정해진 것

  • Jetson Xavier는 VCU로 한정액추에이터 제어와 기본 통신만 담당, Jetson Thor의 제어 명령 수신
  • Jetson Thor가 상위 연산 담당관제·주행 플래닝·매핑·퍼셉션, Jetson Xavier와 RJ45 이더넷으로 연결
  • 센서는 뎁스 카메라, 상부 카메라, 고정 LiDAR 조합LiDAR는 Jetson Thor에 직접 연결
  • YOLO 전용 연산 장치 탑재Jetson Thor 쪽 전력 소모를 줄이기 위한 선택
  • 오도메트리는 LiDAR 내장 IMU 사용로봇 내장 IMU는 시프트가 생겨 제외
  • SLAM과 가감속 제어는 자체 개발FAST-LIO2는 실사용 성능 부족, 기본 가감속 로직은 자체 알고리즘에 얹을 수 없음
  • 클라우드는 세 서비스로 시작AWS IoT Greengrass, AWS IoT Core, Amazon Kinesis Video Streams가 핵심, RL 정책만 학습하면 Amazon SageMaker AI 제외
  • 이번 지원은 고객 지원 프로그램파트너 지원이 아니며, 파트너 지원 요청은 별도 파트너 팀 담당
  • 현장 방문은 잦을수록 유리시뮬레이션만으로는 튜닝에 한계, 실측 데이터와 병행

흐름

1Jetson Xavier는 VCU, Jetson Thor는 상위 연산 담당

지금 Vision 60은 내장 Jetson Xavier가 연산을 맡는 제조사 방식입니다. 새 구조에서 Jetson Xavier는 VCU로서 액추에이터 제어와 기본 통신만 맡습니다. 관제·주행 플래닝·매핑·퍼셉션 같은 상위 연산은 새로 올리는 Jetson Thor가 맡고, 제어 명령을 Jetson Xavier로 내려보냅니다. 두 장치는 Vision 60 본체의 RJ45 단자를 통해 이더넷으로 연결합니다. Jetson Thor를 더한 상태의 배터리 구동시간은 아직 재지 않았습니다.

  • 구동시간 기준은 3시간 이상, 추가 장비가 없을 때 기준
  • YOLO 전용 연산 장치를 Jetson Thor에 탑재해 전력 소모 감소 목표
  • 카메라 데이터 경로: Jetson Xavier에 붙은 카메라 영상은 YOLO 추론을 위해 Jetson Thor로 다시 전송 필요
  • 카메라 하위단 직접 연결은 제조사 접근이 열려 있지 않아 보류
  • Jetson Thor 자체 통신은 가능, 옵션에 따라 Wi-Fi가 없는 모델은 분해해 추가

2LiDAR 직결과 자체 SLAM으로 위치추정

Vision 60의 내장 뎁스 카메라 두 개는 바닥을 향해 있고, 전면 광각 카메라 두 개도 퍼셉션에 쓰기 어렵습니다. 센서는 뎁스 카메라, 상부 카메라, 고정 LiDAR 조합으로 갑니다. 로봇 내장 IMU는 시프트가 생겨 오도메트리에 쓰지 않고, 3D LiDAR에 들어 있는 IMU를 씁니다. SLAM은 FAST-LIO2를 검토했지만 실사용 성능이 부족했습니다. 그래서 다층·3D 구조에 맞게 개량한 자체 SLAM을 만들고 있습니다.

  • 공식 기본 센서: RGB 카메라 5대, D435 뎁스 센서 4대
  • 뎁스 카메라 장착 방향은 공식 사양에 없어 확인 불가
  • 3D LiDAR 내장 IMU는 센서 퓨전에 유리
  • FAST-LIO2는 회전형·고정형 LiDAR와 외부 IMU를 지원하는 공개 패키지
  • SLAM 모델 크기: 파라미터가 커지면 내부 연산 부담, 필요한 리소스 규모 미정

3평지·경사는 본체 제어, 계단 전환은 직접 제어 필요

로코모션 제어는 기본적으로 로봇 본체에 맡깁니다. 상위 연산은 전진·회전·방향 같은 추상 명령만 주고, 본체가 보행을 처리합니다. 평지와 경사에서는 이 방식에 문제가 없습니다. 계단을 오르내리며 동작을 바꿀 때는 발 모터단을 직접 제어해야 하고, 가감속 제어도 자체 알고리즘에 얹기 위해 직접 만든 로직으로 바꿉니다. Ghost Robotics가 저수준 제어를 어디까지 열어 줄지는 아직 모릅니다.

  • Ghost Robotics 데이터 개방은 약속과 달리 제한적이라는 우려
  • 제조사 선정 근거: 중국산 제외 후 비교 분석에서 Ghost Robotics가 가장 나음
  • 국내 총판은 KRM이 올해 4월 종료된 뒤 LIG Nex1이 이관, 공식 자료로는 확인 불가
  • LIG Nex1은 2024년 7월 Ghost Robotics 지분 60% 인수(공식 보도자료)
  • LIG Nex1 담당자와 직접 연락 중
  • Seoul Dynamics는 건설 로봇·지게차 로봇 개발 경험 보유

4핵심 AWS 서비스 세 가지와 Amazon S3 데이터 레이크

로봇 데이터를 클라우드로 올리고, 학습한 모델을 다시 로봇에 배포하는 단계가 가장 중요합니다. 이 단계는 AWS IoT Greengrass, AWS IoT Core, Amazon Kinesis Video Streams 세 서비스만 알면 됩니다. Amazon SageMaker AI는 VLA 모델처럼 MLOps 환경이 필요할 때 쓰고, RL 정책만 학습한다면 필요 없습니다. 대량 업로드 레퍼런스는 Amazon S3에 원시 데이터를 L0, 가공 데이터를 L1에 두고 Amazon EKS로 처리합니다. 어떤 데이터를 남기고 시각을 어떻게 맞출지는 지금처럼 직접 개발해야 합니다.

  • 메타 정보는 Amazon DynamoDB에 저장해 구간별 데이터 위치 색인
  • 비디오 데이터의 90% 이상은 쓸모없는 데이터라는 경험
  • Amazon Kinesis Video Streams 재생: 약 4초 지연으로 실시간 시청, 지난 영상도 재생 가능
  • LiDAR 원시 데이터 업로드는 너무 무거워 온프레미스 처리가 더 빠를 가능성
  • 중간 가공 서비스는 쓰지 않고 코드로 처리하는 편이 깔끔하다는 판단
  • 참고 사례: 위로보틱스(VLA·VTLA 학습 데이터 수집), 뉴빌리티(실시간 영상 업로드)

5엣지 YOLO로 거르고 애매한 장면만 VLM에 판단 요청

작년 산업안전 데모는 Unitree Go2에 Jetson Orin을 달고 공장을 순찰하며 쓰러진 사람·화재·제스처를 감지했습니다. YOLO 모델은 클라우드에서 학습한 뒤 AWS IoT Greengrass로 Jetson Orin에 배포했습니다. 영상은 Amazon Kinesis Video Streams로, CPU·메모리·배터리 같은 메트릭은 AWS IoT Core(MQTT)로 올려 Grafana 대시보드에 띄웠습니다. 학습 데이터가 없는 상황은 VLM이 더 잘 판단하므로, 엣지 YOLO의 confidence가 낮을 때만 Amazon Bedrock의 VLM에 판단을 보내는 구성을 권합니다. 이 구성은 네트워크 연결이 전제이며, 완성품이 아니라 직접 개발해야 합니다.

  • 원격 제어: ROS 커맨드 컴포넌트를 AWS IoT Core에 연결해 클라우드에서 MQTT로 명령 전송
  • 학습용 이미지는 Amazon S3에 별도 업로드
  • 순찰 보고서: 에이전트 AI가 영상·위치·메트릭을 종합해 위험 수준과 권고 사항 작성
  • 비용: IoT 서비스가 가장 저렴, Amazon Bedrock은 토큰 기반 과금
  • VLM 후보: Amazon Bedrock에 Anthropic·OpenAI·NVIDIA 등 여러 공급사 모델, 현장 영상으로 테스트 후 선정
  • AI의 로봇 제어 메시지 직접 생성: 미리 정의한 명령이나 결정 트리 없이 이미지를 보고 이동 명령을 만드는 구현도 데모에 포함

6Isaac Sim·Isaac Lab 학습은 로컬에서 정의하고 클라우드로 확장

지금은 PC 한 대에서 Isaac Lab 학습과 시뮬레이션을 함께 돌립니다. 클라우드에서는 학습과 시뮬레이션을 나누고, 공유 스토리지에 체크포인트를 저장해 시뮬레이션에서 불러와 검증합니다. ROS, Isaac Sim, 통신 프로토콜을 설치한 Amazon EC2 한 대를 세팅하면 그대로 복제해 여러 대로 늘릴 수 있습니다. 여러 노드의 경험 데이터는 스토리지로 동기화해 하나의 모델을 함께 학습합니다. 클라우드는 로컬 PC보다 느리므로, 환경과 알고리즘을 로컬에서 먼저 정의하고 대규모 확장 테스트 때 옮기는 것을 권합니다.

  • Isaac Sim AMI: 버튼 하나로 Isaac Sim 설치 환경 실행, AMI는 무료이고 Amazon EC2 비용은 별도
  • AWS Batch 노출 파라미터: 환경 ID, 로봇, 학습 에폭, 노드 수, 노드당 GPU 수, 이터레이션
  • 개별 제어: 복제한 Amazon EC2에 SSH로 접속하거나 DCV GUI로 원격 조작
  • Slurm 같은 HPC 스케줄러로 대규모 Amazon EC2를 직접 제어하는 방법도 가능
  • 학습 결과 확인: 로그는 클라우드에서, 학습된 정책의 동작은 Isaac Sim에서 바로 재생
  • 룰 기반 플래너의 한계: 바닥에 물이 있는 경우 같은 예상 못 한 상황 처리 미해결

7대용량 영상은 SSD 직접 교체가 가장 빠른 방법

로봇이 1시간 동안 찍은 360도 영상을 무선으로 올리면 시간이 매우 오래 걸립니다. 도킹 스테이션과 이더넷으로 연결해 옮기는 방법은 가능하지만, 이더넷 전송은 너무 느리고 다른 통신보다 불안정해 거의 쓰지 않습니다. 가장 빠른 방법은 사람이 SSD를 직접 빼서 옮기는 것입니다. 차선책은 특정 Wi-Fi에 접속하면 자동으로 올리는 방식이지만 밤새 걸렸던 경험이 있고, 올리기 전에 NVIDIA 인코더로 압축하면 용량이 크게 줄어듭니다. 어느 방식을 기본으로 할지는 정하지 않았습니다.

  • Jetson Thor SSD 교체는 그래픽카드를 먼저 떼어내야 하는 작업
  • Jetson Thor 모듈 저장 장치: 1TB NVMe는 개발자 키트 구성품, 모듈은 PCIe로 NVMe를 따로 연결
  • USB SSD를 외부로 빼는 방식도 대안으로 검토
  • 압축 효과: 압축 여부에 따라 10배 이상 차이라는 언급, 공식 수치는 확인 불가
  • NVENC: 2026년 1월부터 Video Codec SDK가 Jetson Thor 인코딩 지원
  • 충전 중 업로드: 충전 시간 동안 업로드를 기다려야 하는 제약

시사점

추정산업안전 데모 구성을 그대로 바탕으로 쓸 수 있습니다. 데모는 Jetson Orin 위 YOLO를 AWS IoT Greengrass로 배포하고, 영상·메트릭·원격 명령을 Amazon Kinesis Video Streams와 AWS IoT Core로 처리했습니다. 시연 뒤 이 프로젝트 구조와 같다는 평가가 나왔습니다. 처음부터 설계하기보다 데모의 Jetson Orin 자리를 Jetson Thor로 바꾸는 편이 빠릅니다.

추정룰 기반 플래너의 약점과 VLM 보완 구성이 맞물립니다. 하드코딩한 플래너는 바닥에 물이 있는 경우 같은 예상 못 한 상황에 약합니다. YOLO confidence가 낮을 때만 VLM에 판단을 넘기는 구성을 이 예외 처리에 쓸 수 있습니다. 다만 클라우드 왕복 지연이 있어 주행 판단이 아니라 상황 판단에만 맞습니다.
