핵심 메시지

Vision 60은 Jetson Thor가 상위 연산을 맡고 Jetson Xavier가 VCU를 맡는 구조로 바뀝니다. 클라우드 연결은 AWS IoT Greengrass·AWS IoT Core·Amazon Kinesis Video Streams 세 서비스로 구성합니다.

  • 연산 구조 — Jetson Thor는 관제·주행 플래닝·매핑·퍼셉션, Jetson Xavier는 액추에이터 제어·기본 통신을 맡는 VCU로 결정
  • AWS 핵심 서비스 — AWS IoT Greengrass·AWS IoT Core·Amazon Kinesis Video Streams 세 가지로 결정, RL 정책만 학습하면 Amazon SageMaker AI는 미사용
  • 교육·투입 일정 — 8월 말~9월 초 투입 전 세팅 완료 목표, 집중 교육 아젠다와 날짜는 AWS 팀이 산출
  • 제조사 개방 범위 — 계단 전환용 발 모터 제어와 카메라 재배치에 필요한 Ghost Robotics 하위단 접근 범위 미확인
  • 대용량 데이터 회수 — SSD 물리 교체가 가장 빠르지만 사람 개입 필요, 회수 방식 미정

백그라운드

  • 교육 방향 확정 필요 — Vision 60 아키텍처를 먼저 확인하고 교육 방향을 빨리 정하기 위한 회의
  • 에셋 재작업 방지 — 현장 방문 전에 만든 에셋이 아키텍처와 맞지 않아 쓰지 못한 전례
  • 연산 구조 변경 대상 — Ghost Robotics 방식으로 구성된 Vision 60을 Jetson Thor 중심 구조로 변경
  • 로봇 선정 경위 — 중국산 제외 조건으로 Spot 등 후보를 비교한 결과 Ghost Robotics 선정
  • 투입 시점 — 8월 중순부터 수동 운용으로 현장 투입 가능, 8월 말~9월 초 투입 전 세팅 완료 목표

회의 요약

#

주요 논의

  • 연산 역할 분담 — Jetson Xavier는 VCU, Jetson Thor는 상위 연산을 맡고 둘은 RJ45 이더넷으로 연결
  • 센서 재배치 — 내장 카메라가 바닥을 향해 상부 카메라를 새로 달고 LiDAR는 Jetson Thor에 직결
  • 제조사 데이터 개방 — Ghost Robotics의 실제 데이터 개방은 약속보다 좁을 가능성, 개방 범위 미확인
  • 자체 개발 범위 — 오도메트리는 LiDAR 내장 IMU, SLAM은 FAST-LIO2 대신 자체 개발, 가감속 제어는 Jetson Thor에서 담당
  • AWS 핵심 서비스 — AWS IoT Greengrass·AWS IoT Core·Amazon Kinesis Video Streams 세 가지, 데이터는 Amazon S3에 L0/L1/L2 계층으로 저장
  • 산업안전 데모 구조 — 엣지에서 YOLO로 먼저 거르고 신뢰도가 낮은 경우만 Amazon Bedrock VLM으로 판단
  • 시뮬레이션 학습 — 로컬 PC에서 환경·알고리즘을 정의하고 대규모 확장 테스트 단계에만 Amazon EC2·Isaac Sim으로 이전
  • 대용량 영상 회수 — SSD 교체·Wi-Fi 자동 업로드·NVIDIA 인코더 압축 후보 비교, 방식 미정
  • 교육·현장 일정 — AWS 팀이 집중 교육 아젠다·날짜·워크숍 일정을 산출하고, 문의는 메일 루프로 접수

전체 구조

  1. ①

    Jetson Xavier는 VCU 담당

    • Vision 60 내장 기존 컴퓨터, 새 구조에서 액추에이터 제어·기본 통신 담당
    • Jetson Thor의 제어 명령 수신, 모터와 내장 카메라 연결
    • 평지·경사 보행은 본체에 위임, 계단 전환 시 발 모터단 직접 제어 필요
    • Ghost Robotics 저수준 접근 범위 미확인
  2. ②

    Jetson Thor는 상위 연산 담당

    • 관제·주행 플래닝·매핑·퍼셉션·추론 담당
    • 개발자 키트 대신 모듈 사용, 1TB 저장 장치에 SSD 추가 계획
    • 1TB NVMe는 개발자 키트 구성품, 모듈은 캐리어 보드에 NVMe 별도 구성 필요
    • 소비 전력 40–130 W, 전력 절감용 YOLO 전용 연산 장치 탑재 계획
  3. ③

    센서 조합은 뎁스 카메라·상부 카메라·고정 LiDAR

    • 내장 뎁스 카메라와 전면 광각 카메라는 바닥 방향이라 퍼셉션에 부족
    • 퍼셉션용 상부 카메라 신규 장착
    • 고정형 LiDAR는 Jetson Thor에 직결
    • Vision 60 기본 센서는 RGB 카메라 5대·D435 뎁스 센서 4대, 장착 방향은 사양에 미기재
  4. ④

    Jetson Xavier–Jetson Thor 간 RJ45 이더넷

    • Vision 60의 RJ45 커넥터로 이더넷 통신
    • Jetson Xavier 쪽 카메라 데이터를 YOLO에 쓰려면 Jetson Thor로 재전송 필요
    • 하위단 접근이 막혀 있어 카메라 이전 곤란
    • 제어 명령과 센서 데이터가 함께 실릴 때의 대역폭·지연 미검토(추정 리스크)
  5. ⑤

    AWS IoT Greengrass·AWS IoT Core가 핵심 파이프라인

    • AWS IoT Greengrass는 클라우드에서 학습한 모델을 Jetson 계열 장치에 배포
    • AWS IoT Core는 MQTT로 메트릭 수집·원격 제어 명령 전달
    • 처음 혼자 구성하기는 어렵지만 워크숍 한 번으로 파이프라인 습득 가능
    • 비용은 IoT 서비스가 가장 저렴
  6. ⑥

    Amazon Kinesis Video Streams로 실시간 영상

    • WebRTC나 HLS로 실시간 시청
    • 지연 약 4초, 공식 문서상 HLS 지연은 보통 3–5초
    • 지난 영상을 ROS 백 재생처럼 되돌려 보기 가능
    • 현장 네트워크 연결 전제
  7. ⑦

    Amazon S3 데이터 레이크와 Amazon EKS 처리

    • Amazon S3에 L0 원시·L1 가공·L2 계층, 하이브 파티셔닝으로 저장
    • Amazon EKS로 처리, 메타 정보는 DynamoDB에 저장
    • 비디오 데이터 90% 이상이 불필요해 세그먼트·큐레이션 필요
    • LiDAR 원시 데이터는 무거워 온프레미스 처리가 더 빠를 가능성
  8. ⑧

    신뢰도가 낮은 경우만 Amazon Bedrock VLM

    • 엣지에서 YOLO·결정 트리로 1차 판단
    • confidence가 낮은 이미지만 Amazon Bedrock VLM으로 전송
    • 클라우드 왕복과 추론 시간 때문에 선별 전송, 과금은 토큰 기준
    • 모델은 현장 영상으로 테스트해 선정
  9. ⑨

    오프라인 데이터 회수 방식 미정

    • 1시간 360도 영상 무선 업로드에 매우 긴 시간 소요
    • SSD 물리 교체가 가장 빠르지만 사람 개입 필요
    • 특정 Wi-Fi 자동 업로드는 밤새 소요, 이더넷은 느리고 불안정
    • NVIDIA 인코더 압축은 대안 후보

결정 사항 11건

  • Jetson Xavier는 VCU, Jetson Thor는 상위 연산일반적인 자율주행·로보틱스 구조와 같게 가져가며, Jetson Xavier는 Jetson Thor의 제어 명령을 받습니다.
  • Jetson Xavier–Jetson Thor 간 RJ45 이더넷 통신Vision 60에 있는 기존 인터페이스를 씁니다. 대역폭과 지연은 아직 검토하지 않았습니다.
  • LiDAR 직결과 상부 카메라 신규 장착내장 카메라가 바닥을 향하고 하위단 카메라 접근도 열려 있지 않아 뎁스 카메라·상부 카메라·고정 LiDAR 조합으로 갑니다.
  • 오도메트리는 LiDAR 내장 IMU로 구성Vision 60 내장 IMU는 시프트가 생겨 쓰지 않습니다.
  • FAST-LIO2 대신 자체 SLAM 사용FAST-LIO2는 실사용 성능이 부족해 다층·3D 구조에 맞게 개량한 자체 SLAM을 개발합니다.
  • 가감속 제어는 Jetson Thor의 자체 로직Vision 60 기본 로직으로는 자체 알고리즘을 얹을 수 없어 Vision 60은 기본 제어만 맡습니다.
  • AWS 핵심 서비스는 AWS IoT Greengrass·AWS IoT Core·Amazon Kinesis Video StreamsRL 정책만 학습하면 Amazon SageMaker AI는 쓰지 않고, VLA 등 별도 모델 학습이 생기면 다시 검토합니다.
  • 현장 투입은 수동 운용부터시뮬레이션만으로는 튜닝에 한계가 있습니다. 8월 중순부터 수동 운용으로 자주 투입하고 실측 데이터로 튜닝합니다.
  • 집중 교육 아젠다는 AWS 팀이 산출기초 교육 대신 집중 교육으로 8월 말~9월 초 투입 전에 세팅을 끝내고 에셋 재작업을 막습니다.
  • 문의 창구는 메일 루프전문가 네 명 중 한 명이 답하고 필요한 에셋을 공유합니다.
  • 고객 지원 프로그램으로 진행AWS 팀은 원래 파트너를 지원하지 않으므로 이번 지원은 고객 지원 프로그램으로 운영합니다.

논의 흐름

#

주제 제목을 누르면 접고 펼칠 수 있습니다.

1Jetson Xavier는 VCU, Jetson Thor는 상위 연산 담당

Jetson Thor 중심 구조로 변경

Vision 60은 지금 Ghost Robotics 방식으로 구성돼 있습니다. 이번 프로젝트는 이 구조를 Jetson Thor 중심으로 바꿉니다. 구조는 일반적인 자율주행·로보틱스와 같습니다. 하위 VCU 위에 인지와 자율 판단을 맡는 상위 연산을 둡니다.

두 컴퓨터의 역할

Vision 60에 내장된 Jetson Xavier는 VCU 역할을 맡아 액추에이터 제어와 기본 통신을 합니다. Jetson Xavier는 Jetson Thor의 제어 명령을 받습니다. Jetson Thor는 관제, 주행 플래닝, 매핑을 맡습니다. 두 컴퓨터는 Vision 60에서 나오는 RJ45 커넥터로 이더넷 통신을 합니다.

센서 재배치

내장 뎁스 카메라 두 개는 앞쪽에 있지만 바닥을 향합니다. 전면 광각 카메라 두 개도 바닥만 봐서 퍼셉션에 쓰기 어렵습니다. 그래서 상부에 퍼셉션용 카메라를 따로 달고 고정형 LiDAR는 Jetson Thor에 직접 연결합니다. 최종 센서 조합은 뎁스 카메라, 상부 카메라, 고정 LiDAR입니다.

구동시간과 전력

기본 구동시간은 3시간 이상으로 봅니다. 다만 이 값은 추가 장비가 없을 때 기준입니다. 전력 소모를 줄이려고 Jetson Thor 쪽에 YOLO 전용 연산 장치를 올립니다. Jetson Thor를 단 상태의 구동시간은 아직 측정하지 않았습니다(추정).

카메라 데이터 재전송 문제

Jetson Xavier에 붙은 카메라 데이터를 YOLO에 쓰려면 이더넷으로 Jetson Thor에 다시 넘겨야 합니다. 카메라를 하위단에서 옮기려 했지만 접근이 열려 있지 않습니다. 현장에 가기 전에 기존 Vision 60 제품을 직접 확인하는 편이 좋습니다.

2Ghost Robotics 선정, 데이터 개방 범위는 미확인

선정 조건과 결과

로봇 선정 조건은 중국산 제외였습니다. Spot 등 후보를 비교 분석한 결과 Ghost Robotics가 가장 나았습니다. Seoul Dynamics는 건설 로봇 분야에서 지게차 로봇을 개발한 곳입니다.

약속보다 좁은 데이터 개방

Ghost Robotics는 데이터를 어느 정도 열어 주기로 했습니다. 하지만 실제 개방 범위는 약속보다 좁을 가능성이 큽니다(추정). 이 범위에 따라 카메라 재배치와 하위단 제어 가능 여부가 정해집니다.

공급 경로 변경

국내 총판은 KRM이었지만 올해 4월에 끝났고 LIG Nex1이 넘겨받았습니다. 지금은 LIG Nex1과 직접 연락하고 있습니다. 방법이 없지는 않다는 답을 받았습니다. 이 답이 데이터·하위단 접근을 가리키는지는 분명하지 않습니다(추정).

공식 자료 대조

LIG Nex1은 2024년 7월 Ghost Robotics 지분 60%를 2억4천만 달러에 인수했습니다. KRM 종료와 총판 이관은 공식 자료로 확인하지 못했습니다. 개방 범위는 서면으로 확인해야 합니다.

3오도메트리·SLAM·가감속 제어는 자체 개발

Jetson Thor 저장 장치와 통신

Jetson Thor는 개발자 키트가 아니라 더 작은 모듈을 씁니다. 저장 장치는 1TB를 쓰고 필요하면 내부를 열어 1TB SSD를 하나 더 넣습니다. 공식 사양상 1TB NVMe는 개발자 키트 구성품이라 모듈은 캐리어 보드에 NVMe를 따로 구성해야 합니다. 통신은 Jetson Thor 자체로 가능하지만 Wi-Fi가 없는 구성은 직접 열어 손봅니다.

LiDAR 내장 IMU로 오도메트리

Vision 60 내장 IMU는 시프트가 생겨 오도메트리에 쓰지 않습니다. 대신 LiDAR에 포함된 IMU로 오도메트리를 만듭니다. 뎁스 카메라에도 IMU가 있지만 LiDAR와 센서 퓨전하는 부담이 큽니다. 3D LiDAR는 보통 IMU가 내장돼 있어 퓨전에 유용합니다.

FAST-LIO2 대신 자체 SLAM

FAST-LIO2를 검토했지만 실사용 성능이 부족했습니다. 그래서 개량해 다층·3D 구조에 쓸 수 있는 자체 SLAM을 만들고 있습니다. SLAM·내비게이션 연산 자원은 많을수록 좋지만 모델 파라미터가 너무 커지면 부담이 됩니다.

가감속 제어는 Jetson Thor에서

Vision 60에도 가감속 제어가 있습니다. 하지만 이 로직으로는 자체 알고리즘을 얹을 수 없습니다. 그래서 Vision 60은 기본 제어만 하고 직접 만든 가감속 제어를 Jetson Thor에서 내립니다.

계단 전환은 발 모터 제어 필요

로코모션은 앞으로 가기·회전 같은 추상 명령만 주고 로봇 본체에 맡깁니다. 평지와 경사는 이 방식으로 문제가 없습니다. 계단을 오르며 동작을 전환할 때는 발 모터단을 직접 제어해야 합니다. 이 접근이 가능한지는 아직 모릅니다.

4AWS 핵심 서비스 세 가지와 Amazon S3 계층 저장

필요한 서비스는 세 가지

가장 중요한 단계는 데이터 수집·업로드와 학습 모델 배포입니다. 이 단계에 AWS IoT Greengrass와 AWS IoT Core를 씁니다. 실시간 영상은 Amazon Kinesis Video Streams로 WebRTC나 HLS 형태로 봅니다. 나머지 서비스는 필수가 아니며 이 세 가지만 기억하면 됩니다.

Amazon SageMaker AI는 조건부

RL 정책만 시뮬레이션에 연결해 학습한다면 Amazon SageMaker AI는 이번에 쓰지 않아도 됩니다. VLA 모델처럼 별도 모델을 학습하면 MLOps 환경이 필요하고 그때 Amazon SageMaker AI가 유용합니다. Amazon Bedrock은 LLM 서빙 서비스입니다.

레퍼런스 데이터 흐름

원시 데이터는 Amazon S3에 저장하고 Amazon EKS로 처리한 뒤 다시 저장합니다. Amazon EKS는 여러 대의 Amazon EC2를 한꺼번에 오케스트레이션하는 쿠버네티스 서비스입니다. 이 구성은 벌크 업로드용 글로벌 레퍼런스입니다. 어떤 데이터를 취득하고 버릴지, 타임스탬프를 어떻게 맞출지는 직접 개발해야 합니다.

L0/L1/L2 계층 저장

Amazon S3에 L0 원시, L1 가공, L2 계층을 두고 하이브 파티셔닝으로 저장합니다. 인덱싱과 구간 메타 정보는 DynamoDB에 넣고 L1 데이터로 학습합니다. 비디오 데이터의 90% 이상은 쓸모가 없어 세그먼트가 필요합니다. 중간 가공 서비스보다 직접 코드로 처리하는 편이 깔끔합니다.

LiDAR 데이터와 Isaac Lab

LiDAR 원시 데이터도 업로드할 수 있지만 너무 무거워 온프레미스 처리가 더 빠를 수 있습니다. Isaac Lab은 학습과 시뮬레이션을 분리해 하나의 스토리지에서 체크포인트를 공유하며 분산 처리할 수 있습니다. Isaac Sim이 설치된 AMI는 무료입니다. Amazon EC2 인프라 비용은 따로 냅니다.

5산업안전 데모 구조 재사용, 저신뢰 판단만 Amazon Bedrock VLM

산업안전 로봇 데모 구성

작년에 AWS 부스용으로 만든 데모는 Unitree Go2가 공장을 돌며 위험 현장과 쓰러진 사람을 감지하고 보고합니다. 로봇 위 RGB-D 카메라 영상은 Amazon Kinesis Video Streams로 실시간 재생합니다. YOLO가 도움 요청·하트 같은 제스처를 인식합니다. 관리자는 웹페이지에서 원격 조종하고 에이전트 AI가 만든 보고를 받습니다.

엣지와 클라우드 연결

모델 학습은 클라우드에서 하고 AWS IoT Greengrass로 Jetson Orin에 배포했습니다. Jetson Orin의 CPU·메모리·배터리는 MQTT로 올려 Grafana 대시보드에서 봅니다. 로봇 하드웨어는 ROS로 통신하고, AWS IoT Core와 연결된 커맨드 컴포넌트가 MQTT 명령을 ROS로 넘깁니다. 이 구성은 완성품이 아니어서 직접 개발해야 합니다. 실시간 구성은 네트워크 연결이 전제입니다.

YOLO 우선, 저신뢰만 VLM

단순 크랙은 YOLO로 충분합니다. 학습 데이터가 없는 상황은 파운데이션 모델이 더 잘 판단할 수 있습니다. 그래서 엣지에서 YOLO와 결정 트리로 먼저 거르고 confidence가 낮을 때만 Amazon Bedrock으로 보냅니다. 클라우드 왕복과 추론에 시간이 걸리기 때문입니다.

비용과 모델 선정

비용은 IoT 서비스가 가장 저렴합니다. Amazon Bedrock은 토큰 기준으로 과금하며 예상보다 저렴합니다. Amazon Bedrock에는 Anthropic·OpenAI·NVIDIA 등 여러 공급사 모델이 있습니다. 현장에 특화된 모델은 없어 현장 영상으로 테스트해 가장 정확한 모델을 고릅니다.

이 프로젝트와의 관계

데모 구조는 이 프로젝트의 센서·로봇 활용 구조와 거의 같습니다. 룰 기반 하드코딩 플래너는 잘 돌지만 바닥에 물이 있는 경우 같은 예상 못 한 상황에 약합니다. VLM 판단은 이런 상황을 맡을 수 있습니다(추정).

6Isaac Sim 학습은 로컬 정의 후 확장 단계에만 클라우드

기존 시스템 그대로 재현

Isaac Sim 환경에서도 기존 하드웨어 시스템, 플래닝 알고리즘, 통신 규약을 그대로 구현할 수 있습니다. Amazon EC2 한 대에 ROS, Isaac Sim, 통신 프로토콜을 한 번 세팅하고 복제해 씁니다. 최소 한 대는 현재 시스템에 맞춰 세팅해야 합니다.

일괄 제어와 개별 제어

여러 Amazon EC2 인스턴스의 파라미터와 리워드는 한꺼번에도, 개별로도 제어할 수 있습니다. 일괄 제어는 AWS Batch에 파라미터를 노출해 설정합니다. 샘플 에셋의 노출 파라미터는 Isaac Lab 환경 ID, 로봇 종류, 학습 에폭, 태스크, 노드당 GPU 수, 이터레이션입니다. 개별 제어는 SSH로 접속하거나 DCV 원격 GUI로 조작합니다. 대규모 제어에는 Slurm 클러스터도 쓸 수 있습니다.

다중 노드 학습

노드 수를 설정하면 여러 대의 PC를 한꺼번에 제어합니다. 여러 노드의 경험 데이터는 공유 스토리지로 동기화해 하나의 모델을 학습합니다. 스토리지가 클라우드에 있어 매번 SSD를 비울 필요가 없습니다. 로그는 클라우드에서 확인하고 학습된 정책은 Isaac Sim에서 바로 봅니다.

로컬에서 먼저 정의

클라우드 학습은 로컬 PC에서 강화학습과 Isaac Sim을 돌리는 것보다 느립니다. 그래서 로컬에서 환경과 알고리즘을 먼저 정의하고 대규모 확장 테스트 때만 클라우드로 옮깁니다. 보상 설계, 학습 시작 방법, 환경 세팅 제어 방식은 아직 고민 중입니다.

7대용량 영상 회수 방식은 미정

무선 업로드의 한계

1시간 동안 움직이며 찍은 360도 영상을 무선으로 올리는 데 매우 오래 걸렸습니다. 로봇과 도크를 이더넷으로 연결해 옮긴 뒤 도크에서 올리는 방식도 가능합니다. 하지만 이더넷은 매우 느리고 다른 통신 방법보다 불안정해 거의 쓰지 않습니다.

SSD 물리 교체

저장 장치를 물리적으로 떼어 옮기는 방법이 가장 빠릅니다. 대신 사람이 대기하다 떼어 옮기고 다시 꽂아야 합니다. Jetson Thor 내부 SSD는 위에 있는 부품을 먼저 떼야 해서 교체가 번거롭습니다. 외부 포트에 USB SSD를 달아 로직으로 저장하고 떼어 내는 방안도 후보입니다.

Wi-Fi 자동 업로드

창고 진입처럼 특정 Wi-Fi 망에 붙는 순간 자동으로 올리는 방식도 있습니다. 이 방식도 밤새 걸렸습니다. 충전하는 동안 업로드하는 방안도 후보입니다.

용량 줄이기

카메라 데이터는 포인트 이미지 촬영이나 타임랩스 촬영으로 가볍게 하는 방안을 생각하고 있습니다(추정). NVIDIA 인코더로 압축하면 10배 이상 줄어든다는 수치는 공식 자료에 없고 코덱·비트레이트에 따라 달라집니다. NVIDIA Video Codec SDK는 2026년 1월부터 Jetson Thor 인코딩을 지원합니다. 어떤 회수 방식으로 갈지는 아직 정하지 않았습니다.

88월 말~9월 초 투입 전 세팅 완료 목표

현장 방문 계획

현장 방문은 용인 현장 중심으로 두 차례 나눠 들어가는 안이 기본입니다. 울산은 시험장으로 쓰기 어렵습니다. Amazon AI 데이터센터 현장이 가장 적합할 가능성이 있습니다(추정). 방문은 하루 종일 걸립니다.

수동 운용으로 시작

시뮬레이션을 잘 만들어도 실측 데이터로 튜닝해야 해서 로봇은 현장에 자주 갈수록 좋습니다. 처음에는 자율주행 없이 수동 운용으로 갑니다. 8월 중순 정도부터 투입이 가능합니다. 용인 현장에서 데이터를 실측하고 플랜트 LiDAR 스캔 데이터를 받는 방안도 있습니다.

집중 교육과 워크숍

AWS 팀이 기초 교육 대신 집중 교육 아젠다를 짜고 가능한 날짜를 빠르게 뽑습니다. 워크숍 형식·일정·아젠다도 함께 뽑습니다. 8월 말~9월 초 투입 전까지 세팅을 끝내는 것이 목표입니다. 세팅 이후에는 Q&A 세션을 이어 갑니다.

지원 방식과 문의 창구

AWS 팀은 원래 고객만 지원하고 파트너 지원은 별도 파트너 팀이 맡습니다. 이번 건은 고객 지원 프로그램으로 운영합니다. 궁금한 점은 망설이지 말고 메일 루프로 보냅니다. 전문가 네 명 중 한 명이 답하고 에셋을 공유합니다.

3사의 기대

SK에게는 건설·건축 산업의 첫 사례입니다. AWS는 이 사례를 외부에 공유하고 발표하려 합니다. Seoul Dynamics는 파트너로 함께 소개됩니다.
