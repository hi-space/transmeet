비전 유통 아키텍처 변경 방안 논의

2026-07-27 10:33–12:24, 1시간 50분

Vision 60 의 상위 연산은 Jetson Thor 가 맡고 Jetson Xavier 는 VCU 로 남기는 구조로 바꾸기로 했습니다.

클라우드는 AWS IoT Greengrass, AWS IoT Core, Amazon Kinesis Video Streams 세 서비스를 중심으로 구성합니다. 8월 말~9월 초 현장 투입 전까지 교육과 워크숍을 거쳐 세팅을 끝내는 것이 목표입니다. Ghost Robotics 의 저수준 제어 개방 범위와 장비 추가 후 구동시간은 아직 모릅니다. 대용량 영상 회수 방식도 아직 정하지 않았습니다.

한눈에 보기

  • 연산 구조 — Jetson Thor는 관제·주행 플래닝·매핑, Jetson Xavier는 VCU로 역할 분리 결정
  • 센서 구성 — LiDAR는 Jetson Thor 직결, 퍼셉션용 상부 카메라 별도 장착
  • AWS 서비스 — AWS IoT Greengrass·AWS IoT Core·Amazon Kinesis Video Streams 세 가지가 핵심, RL 정책만 학습하면 Amazon SageMaker AI는 불필요
  • 일정 — 8월 중순 수동 운용 투입, 8월 말~9월 초 투입 전 세팅 완료 목표
  • 남은 위험 — 발 모터 저수준 제어 접근 범위와 장비 추가 후 구동시간 미확인

회의 요약

  1. ①

    Jetson Xavier는 VCU 담당

    Vision 60 에 내장된 Jetson Xavier 는 VCU 로 남아 액추에이터 제어와 기본 통신을 맡습니다. 기존 내장 센서와 모터는 그대로 Jetson Xavier 에 연결돼 있습니다. Jetson Xavier 는 Jetson Thor 의 제어 명령을 받아 실행합니다. 공식 사양상 내장 컴퓨터는 Jetson Xavier(32GB RAM, 2TB NVMe SSD)입니다.

  2. ②

    Jetson Thor가 상위 연산 담당

    Jetson Thor 가 관제, 주행 플래닝, 매핑, YOLO 추론을 맡습니다. Jetson Xavier 와는 Vision 60 의 RJ45 커넥터로 이더넷 통신을 합니다. Jetson Xavier 쪽 카메라 데이터도 이 링크로 Jetson Thor 에 넘겨야 합니다. 이 링크의 대역폭과 지연은 아직 검토하지 않았습니다.

  3. ③

    LiDAR와 상부 카메라 추가

    LiDAR 는 Jetson Thor 에 직접 연결합니다. 내장 뎁스 카메라와 전면 광각 카메라가 모두 바닥을 향해 전방 퍼셉션이 부족하므로, 상부에 퍼셉션용 카메라를 따로 답니다. 기존 카메라의 하위단 접근이 열려 있지 않아 내장 카메라를 깊이 활용하기도 어렵습니다.

  4. ④

    계단 전환 시 발 모터 제어 필요

    평지와 경사에서는 로봇 본체에 전진·회전 같은 추상 명령만 주면 됩니다. 계단 오르기로 동작을 바꿀 때는 발 모터단을 직접 제어해야 합니다. Ghost Robotics 가 이 수준까지 접근을 열어 줄지는 아직 모릅니다.

  5. ⑤

    장비 추가 후 구동시간 미측정

    기본 구동시간은 3시간 이상이지만 추가 장비가 없을 때 기준입니다. Jetson Thor 소비 전력은 공식 사양상 40–130 W 이므로 전력 분배와 구동시간이 달라질 수 있습니다. YOLO 전용 연산 장치를 올려 전력 소모를 줄일 계획입니다. 장비를 단 뒤의 실제 구동시간은 아직 재지 않았습니다.

  6. ⑥

    핵심 AWS 서비스 세 가지

    데이터 수집과 모델 배포는 AWS IoT Greengrass 와 AWS IoT Core 가, 실시간 영상은 Amazon Kinesis Video Streams 가 맡습니다. RL 정책만 학습한다면 Amazon SageMaker AI 는 이번에 쓰지 않아도 됩니다. 실시간 관제는 네트워크 연결이 전제입니다. 파이프라인은 직접 개발해야 하므로 워크숍에서 실습할 계획입니다.

  7. ⑦

    낮은 신뢰도 판단만 Amazon Bedrock VLM으로

    엣지에서 YOLO 와 결정 트리로 먼저 판단하고, confidence 가 낮을 때만 Amazon Bedrock 의 VLM 에 판단을 요청합니다. 클라우드 왕복과 추론에 시간이 걸리므로 모든 판단을 보내지 않습니다. 현장 영상에 가장 정확한 모델은 테스트한 뒤 고릅니다.

  8. ⑧

    대용량 데이터 회수 경로 미정

    1시간 동안 찍은 360도 영상은 무선으로 올리면 매우 오래 걸립니다. SSD 물리 교체가 가장 빠르지만 Jetson Thor 는 위의 그래픽카드를 먼저 떼야 합니다. 특정 Wi-Fi 자동 업로드와 NVIDIA 인코더 압축도 후보입니다. 어느 방식으로 갈지는 정하지 않았습니다.

  9. ⑨

    Isaac Sim/Isaac Lab 클라우드 학습

    Isaac Sim 이 설치된 AMI 로 Amazon EC2 하나를 세팅한 뒤 복제하고, AWS Batch 로 여러 Amazon EC2 의 학습 파라미터를 한꺼번에 설정합니다. 클라우드 학습은 로컬 PC 보다 느립니다. 그래서 로컬에서 환경과 알고리즘을 먼저 정한 뒤 대규모 확장 테스트 단계에서 클라우드로 옮깁니다.

논의 흐름

1Jetson Xavier는 VCU, Jetson Thor는 상위 연산 담당

Vision 60 은 Ghost Robotics 의 4족 보행 로봇이고 내장 컴퓨터로 Jetson Xavier 를 씁니다. 새 구조는 대부분의 자율주행·로보틱스 시스템처럼 하위 제어 층과 상위 인지·플래닝 층으로 나눕니다. Jetson Xavier 는 VCU 역할을 맡아 액추에이터 제어와 기본 통신을 처리합니다. 관제, 주행 플래닝, 매핑 같은 상위 연산은 새로 올리는 Jetson Thor 가 맡습니다. 두 컴퓨터는 Vision 60 에서 나오는 RJ45 커넥터로 이더넷 통신을 합니다.

기존 내장 센서와 통신은 Jetson Xavier 에 그대로 둡니다. 전면의 뎁스 카메라 두 개와 광각 카메라 두 개는 모두 바닥을 향해 전방 퍼셉션에 쓰기 어렵습니다. 그래서 상부에 퍼셉션용 카메라를 따로 달고, LiDAR 는 Jetson Thor 에 직접 연결합니다. Jetson Thor 에서 YOLO 를 돌리면 Jetson Xavier 쪽 카메라 데이터를 이더넷으로 다시 넘겨야 합니다. 이 링크의 대역폭과 지연은 아직 검토하지 않았습니다.

  • 센서 조합 — 뎁스 카메라 + 상부 카메라 + 고정 LiDAR
  • 공식 사양 — 기본 센서 RGB 카메라 5대·D435 뎁스 센서 4대, 카메라 장착 방향은 사양에 미기재
  • 구동시간 — 기본 3시간 이상, 추가 장비 없을 때 기준
  • 전력 절감 — Jetson Thor 쪽에 YOLO 전용 연산 장치 탑재 계획, 장치 명칭 미확인
  • 카메라 하위단 — 접근이 열려 있지 않아 기존 카메라 활용 제한
  • 사전 확인 — 투입 전 기존 Vision 60 제품 직접 확인 권장

2Ghost Robotics 데이터 개방은 기대보다 제한적, LIG Nex1 경로로 확인 중

Vision 60 플랫폼은 중국산 제외를 기준으로 골랐습니다. Rainbow, Spot 등 후보를 비교한 결과 Ghost Robotics 가 가장 나았습니다. Ghost Robotics 는 데이터를 어느 정도 열어 주겠다고 했지만 실제 개방 범위는 그보다 좁다는 우려가 있습니다. 이 범위에 따라 발 모터 제어와 카메라 하위단 활용 가능 여부가 갈립니다.

국내 총판은 KRM 이었으나 올해 4월 종료되고 LIG Nex1 이 넘겨받았습니다. 다만 총판 이관은 공식 자료로 확인하지 못했습니다. LIG Nex1 은 2024년 7월 Ghost Robotics 지분 60%를 2억 4천만 달러에 인수해 경영권을 가졌습니다. LIG Nex1 과는 직접 연락하고 있습니다. LIG Nex1 은 방법이 없지는 않다고 답했습니다. 데이터 개방 수준과 하위단 접근 범위는 아직 확인하지 못했습니다.

  • 선정 기준 — 중국산 제외
  • 비교 후보 — Rainbow·Spot 비교 후 Ghost Robotics 선택
  • 협력사 — Seoul Dynamics, 건설 로봇(지게차 로봇) 경험 보유
  • 총판 — KRM 4월 종료 후 LIG Nex1 이관, 공식 자료 미확인
  • 인수 — LIG Nex1, 2024년 7월 Ghost Robotics 지분 60% 인수(2억 4천만 달러)

3오도메트리는 LiDAR 내장 IMU, SLAM·가감속 제어는 자체 개발

Vision 60 내장 IMU 는 시프트가 생겨 오도메트리를 만들기 어렵습니다. 그래서 LiDAR 에 들어 있는 IMU 로 오도메트리를 구성합니다. 뎁스 카메라에도 IMU 가 있지만 LiDAR 와 센서 퓨전 부담이 커서 쓰지 않습니다. 3D LiDAR 는 보통 IMU 를 내장하고 있어 퓨전에 유리합니다.

SLAM 은 FAST-LIO2 를 검토했으나 실사용 성능이 부족해 개량한 자체 SLAM 을 개발하고 있습니다. 자체 SLAM 은 다층·3D 구조에 대응하도록 만듭니다. 가감속 제어도 Jetson Thor 에서 직접 만든 로직을 쓰고 Vision 60 은 기본 제어만 맡습니다. 평지와 경사는 로봇 본체에 추상 명령만 주면 되지만, 계단 오르기로 전환할 때는 발 모터단을 직접 제어해야 합니다. 이 접근이 가능한지는 아직 모릅니다.

  • 가감속 제어 이유 — 자체 알고리즘에 얹으려면 Jetson Thor 쪽 직접 구현 필요
  • SLAM 자원 — Jetson Thor 위 SLAM·내비게이션 모델의 자원 규모 미정, 파라미터가 커지면 부담
  • 저장 장치 — 1TB SSD 사용, 다른 프로젝트에서는 내부를 열어 1TB 추가 장착
  • 모듈 사양 — 1TB NVMe 는 개발자 키트 구성품, 모듈은 캐리어 보드에 저장 장치 별도 구성 필요
  • 통신 — Jetson Thor 자체 통신 가능, Wi-Fi 없는 옵션은 열어서 대응

4핵심 AWS 서비스는 AWS IoT Greengrass·AWS IoT Core·Amazon Kinesis Video Streams

AWS 의 모델 관련 서비스는 학습용 Amazon SageMaker AI 와 파운데이션 모델 서빙용 Amazon Bedrock 두 가지입니다. RL 정책만 시뮬레이션에 연결해 학습한다면 Amazon SageMaker AI 는 이번에 필요 없습니다. Amazon SageMaker AI 는 VLA 모델 학습처럼 MLOps 환경이 필요할 때 씁니다. 이번 프로젝트의 핵심은 데이터 수집·업로드와 학습 모델 배포이고, 이 단계는 AWS IoT Greengrass 와 AWS IoT Core 가 맡습니다. 실시간 영상은 Amazon Kinesis Video Streams 로 WebRTC 나 HLS 방식으로 봅니다.

벌크 데이터는 Amazon S3 에 L0(원시), L1(가공), L2 계층으로 저장하고 하이브 파티셔닝 방식을 씁니다. 원시 데이터는 Amazon EKS 에서 여러 Amazon EC2 로 빠르게 처리한 뒤 L1 에 다시 저장합니다. 비디오 데이터의 90% 이상은 쓸모가 없으므로 세그먼트와 큐레이션이 필요합니다. 어떤 데이터를 남기고 버릴지, 타임스탬프를 어떻게 맞출지는 직접 개발해야 합니다. 지금과 달라지는 점은 컴퓨터와 스토리지가 PC 의 SSD 에서 클라우드로 옮겨 가는 것뿐입니다. LiDAR 원시 데이터는 너무 무거워 클라우드 업로드보다 온프레미스 처리가 더 빠를 수 있습니다.

  • 메타 인덱스 — L1 구간 정보는 DynamoDB 에 메타 정보로 저장, L1 데이터로 바로 학습
  • Wirobotics 사례 — AWS IoT Core 로 MQTT 데이터, Amazon Kinesis Video Streams 로 영상 수집, 중간 가공은 직접 코드 작성
  • Neubility 사례 — 이동 로봇의 실시간 영상 업로드 레퍼런스
  • 영상 지연 — Amazon Kinesis Video Streams 약 4초 지연, 공식 문서상 HLS 보통 3–5초
  • 지난 영상 재생 — CCTV·rosbag 재생처럼 지난 영상 다시 보기 가능
  • Isaac Lab 분산 — 학습과 시뮬레이션 분리, 공유 스토리지의 체크포인트로 검증

5엣지 YOLO로 먼저 판단하고 낮은 신뢰도만 Amazon Bedrock VLM으로

작년 AWS 부스의 산업안전 데모는 이 프로젝트와 구조가 거의 같습니다. Unitree Go2 가 공장을 돌며 위험 현장과 쓰러진 사람을 감지하고 리포트를 보냈습니다. YOLO 는 클라우드에서 학습하고 AWS IoT Greengrass 로 Jetson Orin 에 배포했습니다. 영상은 Amazon Kinesis Video Streams 의 WebRTC 로 실시간 재생했습니다. ROS 명령 컴포넌트를 AWS IoT Core(MQTT)에 연결해 클라우드에서 원격 제어했습니다. Jetson Orin 의 CPU·메모리·배터리, 이벤트 감지 횟수, 로그·에러, 실시간 위치는 Grafana 대시보드로 보여 줬습니다.

새 구조에서는 Jetson Thor 위 YOLO 와 결정 트리가 먼저 판단합니다. confidence 가 낮을 때만 영상·위치·메트릭을 묶어 Amazon Bedrock 의 VLM 에 판단을 맡깁니다. 클라우드 왕복과 추론에 시간이 걸리기 때문에 모든 판단을 보내지 않습니다. 단순 크랙은 YOLO 로 충분하고, 학습 데이터가 없는 상황은 VLM 이 더 잘 판단합니다. 이 구성은 기성품이 아니라 직접 개발해야 하며 네트워크 연결이 전제입니다.

  • 비용 — IoT 서비스가 가장 저렴, Amazon Bedrock 은 토큰 기반 과금
  • 모델 선정 — Anthropic·OpenAI·NVIDIA 등 Amazon Bedrock 모델 중 테스트 후 선정
  • 현장 전용 모델 — 현장 전용 파운데이션 모델은 사실상 부재, VLM 의 크랙·산업 현장 인식 성능은 크게 향상
  • 순찰 보고서 — 에이전트 AI 가 위험 수준·권고 사항·근거 영상을 담은 보고서 생성
  • 데이터 저장 — 인식된 이미지는 Amazon S3 에 저장, 학습용으로 별도 업로드
  • 모델명 — 언급된 Claude Sonnet 5·Opus 5 모델명 미확인

6Isaac Sim/Isaac Lab은 Amazon EC2 하나를 복제하고 AWS Batch로 일괄 제어

Isaac Sim 은 AWS 가 제공하는 AMI 로 설치된 환경을 바로 띄웁니다. Amazon EC2 하나에 ROS, Isaac Sim, 통신 프로토콜을 한 번 세팅하면 이를 복제해 그대로 씁니다. 파라미터와 리워드는 한꺼번에 제어할 수도, 개별로 제어할 수도 있습니다. 일괄 제어는 AWS Batch 에 파라미터를 노출해 연결된 여러 Amazon EC2 를 한 번에 설정합니다. 개별 제어는 복제한 Amazon EC2 에 SSH 나 DCV(원격 GUI)로 접속합니다.

AWS Batch 다중 노드 작업은 여러 노드의 경험 데이터를 공유 스토리지로 동기화해 하나의 모델을 함께 학습합니다. 학습 로그는 클라우드에서 보고, 학습된 정책은 Isaac Sim 에서 바로 확인합니다. 다만 클라우드 학습은 로컬 PC 보다 느립니다. 그래서 로컬에서 환경·알고리즘·보상을 먼저 정한 뒤 대규모 확장 테스트 단계에서 클라우드로 옮기는 방식을 권합니다.

  • AWS Batch 파라미터 — Isaac Lab Environment ID, 로봇, 학습 에폭, 노드 수, 노드당 GPU 수, 이터레이션, 태스크 값
  • 노드 — 노드 2개 설정 시 PC 2대 동시 제어, 시작 시 실행 명령 지정 가능
  • 체크포인트 — 공식 블로그 사례는 Amazon EFS 에 체크포인트 저장
  • 접속 포트 — SSH TCP 22, DCV TCP 8443
  • 대안 — 대규모 Amazon EC2 제어에 Slurm 같은 HPC 클러스터 스케줄러 사용 가능
  • 비용 — Isaac Sim AMI 무료, g6e·g7e 등 Amazon EC2 인프라 비용 별도

7360도 영상 회수 방식 미정, SSD 교체가 가장 빠르나 Jetson Thor 분해 필요

1시간 정도 움직이며 찍은 360도 영상은 무선으로 올리면 매우 오래 걸립니다. 가장 빠른 방법은 사람이 스토리지를 물리적으로 꺼내 옮기는 것입니다. 하지만 Jetson Thor 에 SSD 를 꽂으려면 위의 그래픽카드를 먼저 떼야 합니다. 기존에 SSD 를 추가한 것도 회수용이 아니라 저장 용량을 늘리기 위해서였습니다.

도킹 스테이션과 로봇을 이더넷으로 연결해 유선으로 옮긴 뒤 도크에서 올리는 방법도 가능은 합니다. 그러나 로봇에서 엣지 장비로 옮기는 이더넷은 매우 느리고 불안정해 거의 쓰지 않습니다. 특정 Wi-Fi 에 접속하면 자동으로 올리는 방법도 밤새 걸린 경험이 있습니다. NVIDIA 인코더로 압축해 용량을 줄이는 방법도 후보입니다. 어느 방식으로 갈지는 정하지 않았습니다.

  • 외부 USB SSD — 외부 USB SSD 를 달아 로직으로 데이터를 빼내는 방법, 구성 미검토
  • 촬영 방식 — 포인트 이미지 촬영 또는 타임랩스 촬영으로 용량 감소 검토
  • 압축률 — 압축 시 10배 이상 차이라는 수치 미확인, 코덱·비트레이트에 따라 다름
  • Jetson Thor 인코딩 — 2026년 1월부터 NVIDIA Video Codec SDK 가 Jetson Thor 인코딩 지원
  • 운용 제약 — 충전 시간 동안 업로드 완료 대기 필요
