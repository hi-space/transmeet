비전 유통 아키텍처 변경 방안 논의

2026-07-27 10:33–12:24, 1시간 50분

Vision 60의 상위 연산은 Jetson Thor가 맡고 Jetson Xavier는 VCU로 두기로 했습니다.

클라우드는 AWS IoT Greengrass·AWS IoT Core·Amazon Kinesis Video Streams 세 서비스를 중심으로 구성합니다. 8월 말~9월 초 현장 투입 전에 집중 교육과 워크숍으로 세팅을 끝내는 것이 목표입니다. Ghost Robotics의 하위단 개방 범위와 Jetson Thor 장착 후 구동시간은 아직 모릅니다. 대용량 데이터 회수 방식도 아직 정하지 않았습니다.

한눈에 보기

  • 연산 분담 — Jetson Xavier는 VCU(액추에이터 제어·기본 통신), Jetson Thor는 관제·주행 플래닝·매핑·퍼셉션 담당으로 결정
  • 핵심 AWS 서비스 — AWS IoT Greengrass·AWS IoT Core·Amazon Kinesis Video Streams 세 가지로 한정, RL 정책만 학습하면 Amazon SageMaker AI는 미사용
  • 일정 — 8월 중순 수동 운용 투입 가능, 8월 말~9월 초 투입 전 세팅 완료 목표
  • 제조사 개방 범위 — 계단 전환 시 발 모터 제어와 자체 가감속 제어는 Ghost Robotics 하위단 개방 범위에 좌우, 범위 미확인
  • 대용량 데이터 회수 — SSD 물리 교체가 가장 빠르지만 사람 개입 필요, 회수 방식 미정

회의 요약

배경·목적

  • 목적 — Vision 60 아키텍처 파악과 교육 방향 조기 확정
  • 재작업 방지 — 아키텍처에 맞지 않게 만든 에셋을 쓰지 못한 경험이 있어 아키텍처 정보 조기 확보 필요
  • 현재 상태 — 현장 방문 전 단계, 에셋 일부 선제작
  • 전환 대상 — 제조사 방식의 Vision 60 구성을 Jetson Thor 중심 구성으로 변경

주요 논의

  • 연산 분담 — Jetson Xavier는 VCU, Jetson Thor는 상위 연산, 퍼셉션 센서는 Jetson Thor 쪽으로 재배치
  • 제조사 — 중국산 제외 조건으로 Ghost Robotics 선정, 데이터 개방 범위는 약속보다 좁을 가능성
  • 자체 개발 범위 — 오도메트리·SLAM·가감속 제어는 자체 개발, 계단 전환은 발 모터단 직접 제어 필요
  • AWS 서비스 — AWS IoT Greengrass·AWS IoT Core·Amazon Kinesis Video Streams가 핵심, 데이터는 Amazon S3 L0/L1/L2 계층 저장
  • 산업안전 데모 — 엣지 YOLO 우선, confidence가 낮은 경우만 Amazon Bedrock VLM으로 상황 판단
  • 시뮬레이션 학습 — 로컬에서 환경·알고리즘 정의 후 대규모 확장 테스트 때만 Amazon EC2로 이전
  • 대용량 데이터 회수 — SSD 물리 교체가 가장 빠르지만 방식 미정
  • 일정·지원 — 8월 중순 수동 운용, 8월 말~9월 초 투입 전 세팅 완료, 교육 아젠다는 AWS 팀이 작성
  1. ①

    Jetson Xavier는 VCU 담당

    • Vision 60 내장 컴퓨터 Jetson Xavier가 액추에이터 제어·기본 통신 담당
    • Jetson Thor의 제어 명령 수신, 모터·내장 카메라도 Jetson Xavier에 연결
    • 평지·경사 보행은 본체에 위임, 계단 전환 시 발 모터단 직접 제어 필요
    • Ghost Robotics의 저수준 접근 허용 범위 미확인
  2. ②

    Jetson Thor가 상위 연산 전담

    • 관제·주행 플래닝·매핑·퍼셉션·추론 담당
    • 개발자 키트 대신 모듈 사용, 1TB 저장 장치에 필요 시 SSD 추가
    • 1TB NVMe는 개발자 키트 구성품, 모듈은 캐리어 보드에 NVMe 별도 구성 필요
    • 소비 전력 40–130 W, YOLO 전용 연산 장치를 함께 올려 전력 절감 계획(장치 명칭 미확인)
  3. ③

    퍼셉션 센서 재배치

    • 내장 뎁스 카메라 2개와 전면 광각 카메라 2개는 바닥 방향이라 퍼셉션에 부적합
    • 퍼셉션용 상부 카메라 신규 장착, 고정형 LiDAR는 Jetson Thor에 직결
    • 센서 조합은 뎁스 카메라 + 상부 카메라 + 고정 LiDAR
    • Vision 60 기본 센서는 RGB 카메라 5대·D435 뎁스 센서 4대, 장착 방향은 사양에서 미확인
  4. ④

    RJ45 이더넷 링크

    • Vision 60의 RJ45 커넥터로 Jetson Xavier와 Jetson Thor 사이 이더넷 통신
    • Jetson Xavier 쪽 카메라 데이터를 YOLO에 쓰려면 Jetson Thor로 재전송 필요
    • 하위단 접근 제한으로 카메라 이전은 어려운 상황
    • 제어 명령과 센서 데이터를 같은 링크에 실을 때의 대역폭·지연 미검토(추정 리스크)
  5. ⑤

    AWS IoT Greengrass·AWS IoT Core

    • 데이터 수집·업로드와 학습 모델 배포 단계의 핵심 서비스
    • AWS IoT Greengrass는 클라우드에서 학습한 모델을 Jetson 계열 엣지 장치에 배포
    • AWS IoT Core는 MQTT로 실시간 메트릭 수집과 원격 제어 명령 전달
    • 파이프라인은 워크숍 1회로 실습 가능, 비용은 IoT 서비스가 가장 저렴
  6. ⑥

    Amazon Kinesis Video Streams

    • 로봇 카메라 영상을 WebRTC·HLS로 실시간 시청
    • 약 4초 지연, 공식 문서상 HLS 지연은 보통 3–5초(범위 1–10초)
    • 지난 영상을 CCTV처럼 재생, ROS 백 재생과 같은 용도
    • 실시간 구성은 현장 네트워크 연결 전제
  7. ⑦

    Amazon S3 데이터 레이크·Amazon EKS

    • Amazon S3에 L0 원시·L1 가공·L2 계층, 하이브 파티셔닝으로 저장
    • Amazon EKS로 데이터 처리, 메타 정보는 DynamoDB에 저장
    • 비디오 데이터 90% 이상이 불필요해 세그먼트·큐레이션 필요
    • LiDAR 원시 데이터는 무거워 온프레미스 처리가 더 빠를 가능성
  8. ⑧

    Amazon Bedrock VLM

    • 엣지에서 YOLO·결정 트리로 1차 필터링
    • confidence가 낮은 경우만 Amazon Bedrock VLM으로 전송, 클라우드 왕복·추론 시간 때문
    • 토큰 기반 과금
    • 현장 영상으로 테스트 후 모델 선정
  9. ⑨

    오프라인 데이터 회수

    • 1시간 360도 영상 무선 업로드에 매우 긴 시간 소요, 이더넷은 느리고 불안정
    • SSD 물리 교체가 가장 빠르지만 사람 개입 필요
    • 특정 Wi-Fi 자동 업로드는 밤새 소요, NVIDIA 인코더 압축이 대안
    • 회수 방식 미정

회의 결과

결정 사항

  • Jetson Xavier는 VCU, Jetson Thor는 상위 연산 담당일반적인 자율주행·로보틱스 구조와 같게 가져가며, Jetson Xavier는 Jetson Thor의 제어 명령을 받습니다.
  • Jetson Xavier–Jetson Thor는 RJ45 이더넷으로 연결Vision 60에 있는 기존 RJ45 인터페이스를 씁니다. 대역폭·지연 검토는 아직 하지 않았습니다(추정).

  • 오도메트리는 LiDAR 내장 IMU로 생성Vision 60 내장 IMU는 시프트가 생겨 쓰지 않습니다.

논의 흐름

1Jetson Thor 상위 연산·Jetson Xavier VCU 구조, 퍼셉션 센서는 Jetson Thor로 재배치

Vision 60은 현재 제조사 방식으로 구성돼 있고, 이번 프로젝트에서 이 구성을 Jetson Thor 중심으로 바꿉니다. 구조는 일반적인 자율주행·로보틱스와 같이 하위 VCU 위에 인지·자율 판단을 맡는 상위 연산을 두는 방식입니다. Vision 60에 내장된 Jetson Xavier가 VCU로서 액추에이터 제어와 통신을 맡고 Jetson Thor의 제어 명령을 받습니다. Jetson Thor는 관제, 주행 플래닝, 매핑을 맡습니다. 두 장치는 Vision 60의 RJ45 커넥터로 이더넷 통신을 합니다.

내장 뎁스 카메라 두 개와 전면 광각 카메라 두 개는 모두 바닥을 향해 퍼셉션에 쓰기 어렵습니다. 이 카메라들은 Jetson Xavier에 연결돼 있어서 Jetson Thor에서 YOLO를 돌리려면 데이터를 이더넷으로 다시 넘겨야 합니다. 하위단을 뜯어 카메라를 옮기는 방법은 접근이 열려 있지 않아 쓰지 못했습니다. 그래서 상부에 퍼셉션용 카메라를 따로 달고, 고정형 LiDAR는 Jetson Thor에 직접 연결합니다. 장비가 늘면 배터리 소모가 커지므로 YOLO 전용 연산 장치를 Jetson Thor 쪽에 올려 전력을 줄일 계획입니다.

  • 센서 조합 — 뎁스 카메라 + 상부 카메라 + 고정 LiDAR
  • 구동시간 기준 — 기본 3시간 이상, 추가 장비가 없을 때 기준
  • 공식 사양 — 연속 보행 3시간 이상, 대기 20시간 이상
  • 미측정 항목 — Jetson Thor·카메라·LiDAR 장착 후 구동시간 미측정(추정)
  • 사전 확인 — 현장 방문 전 기존 Vision 60 실물 확인 권장

2Ghost Robotics 선정, 데이터 개방 범위는 약속보다 좁을 가능성

로봇 선정 요구 사항은 중국산 제외였습니다. Spot 등 후보를 비교 분석했고 그중 Ghost Robotics가 가장 나았습니다. Ghost Robotics는 데이터를 어느 정도 열어 주기로 했습니다. 하지만 실제 개방 범위는 약속보다 좁을 가능성이 큽니다. 이 범위에 따라 계단 전환 제어, 자체 가감속 제어, 카메라 재배치 가능 여부가 달라집니다.

국내 총판이던 KRM은 올해 4월에 총판을 끝냈습니다. 이후 LIG Nex1이 총판을 넘겨받았고, 현재 LIG Nex1과 직접 연락하고 있습니다. LIG Nex1은 2024년 7월 Ghost Robotics 지분 60%를 2억4천만 달러에 인수해 경영권을 확보했습니다. 다만 KRM 종료와 총판 이관은 공식 자료에서 확인하지 못했습니다.

  • Seoul Dynamics — 건설 로봇 분야에서 지게차 로봇 개발 이력
  • 개방 가능성 — 방법이 아예 없지는 않다는 답변, 답변 주체와 대상은 미확인(데이터·접근 관련으로 추정)
  • 모회사 관계 — LIG Nex1이 Ghost Robotics 지분 60% 보유(2024년 7월 인수)
  • 필요 조치 — 데이터·하위단 개방 범위 서면 확인 필요(추정)

3오도메트리·SLAM·가감속 제어는 자체 개발, 계단 전환은 발 모터 직접 제어 필요

Vision 60 내장 IMU는 시프트가 생겨 오도메트리에 쓰지 않습니다. 대신 LiDAR에 내장된 IMU로 오도메트리를 만듭니다. 뎁스 카메라에도 IMU가 있지만 LiDAR와 센서 퓨전을 하는 부담이 큽니다. SLAM은 FAST-LIO2를 검토했으나 실사용 성능이 부족했습니다. 그래서 FAST-LIO2를 개량해 다층·3D 구조에 대응하는 자체 SLAM을 만들고 있습니다.

Vision 60에도 가감속 제어가 있지만 이 로직 위에는 자체 알고리즘을 얹을 수 없습니다. 그래서 Vision 60은 기본 제어만 하고, 직접 만든 가감속 제어를 Jetson Thor에서 내려보냅니다. 로코모션은 앞으로 가기·회전 같은 추상 명령만 주고 로봇 본체에 맡기며, 평지와 경사에서는 이 방식으로 문제가 없습니다. 계단을 오르며 동작을 전환할 때는 발 모터단을 직접 제어해야 합니다. 이 접근이 가능한지는 아직 모릅니다.

  • 저장 장치 — Jetson Thor에 1TB 저장 장치 사용, 필요 시 내부를 열어 1TB SSD 추가
  • 모듈 구성 — 1TB NVMe는 개발자 키트 구성품, 모듈은 PCIe로 NVMe를 붙이는 방식이라 캐리어 보드에 별도 구성 필요
  • 통신 — Jetson Thor 자체 통신 가능, Wi-Fi가 없는 옵션은 직접 열어 개조
  • FAST-LIO2 — 회전형·고정형 LiDAR와 외부 IMU를 지원하는 공개 패키지, 성능 부족은 현장 경험 기준 판단
  • 연산 자원 — SLAM·내비게이션 자원은 많을수록 유리, 모델 파라미터가 지나치게 크면 부담

4핵심 AWS 서비스는 세 가지, 데이터는 Amazon S3 계층 저장

클라우드 구성에서 가장 중요한 단계는 데이터 수집·업로드와 학습 모델 배포입니다. 이 단계에는 AWS IoT Greengrass와 AWS IoT Core를 쓰고, 두 서비스의 파이프라인은 워크숍에서 실습합니다. 실시간 영상은 Amazon Kinesis Video Streams로 WebRTC나 HLS 형태로 봅니다. 나머지 서비스는 필수가 아니어서 이 세 가지만 기억하면 됩니다. RL 정책만 시뮬레이션에 연결해 학습한다면 Amazon SageMaker AI는 이번엔 쓰지 않아도 됩니다.

데이터를 대량으로 올릴 때는 Amazon S3의 원시 데이터를 Amazon EKS로 처리해 다시 저장하는 레퍼런스 구성을 참고합니다. Amazon S3에는 L0 원시, L1 가공, L2 계층을 두고 하이브 파티셔닝으로 저장합니다. 비디오 데이터의 90% 이상은 쓸모가 없어 세그먼트와 큐레이션이 필요합니다. 어떤 데이터를 취득하고 버릴지, 타임스탬프를 어떻게 맞출지는 직접 개발해야 합니다. 기존 방식과 다른 점은 연산 위치와 저장소가 PC 내부 SSD에서 클라우드로 옮겨 간다는 것입니다.

  • Amazon SageMaker AI 조건 — VLA 등 별도 모델 학습 시 MLOps 환경 용도로 재검토
  • Amazon EKS — 여러 Amazon EC2를 묶어 데이터를 빠르게 처리하는 쿠버네티스 서비스
  • DynamoDB — 인덱싱·구간 메타 정보 저장, 학습은 L1 데이터로 진행
  • 다른 로봇 기업 사례 — AWS IoT Core로 MQTT 데이터, Amazon Kinesis Video Streams로 영상 수집, 중간 가공은 별도 서비스 대신 코드로 처리
  • LiDAR 원시 데이터 — 업로드는 가능하지만 무거워 온프레미스 처리가 더 빠를 가능성
  • 서비스 라인 — 데이터 업로드·텔레메트리 시각화·학습·시뮬레이션 네 가지

5산업안전 데모 구조 재사용, YOLO 우선·저신뢰 경우만 VLM 판단

작년에 AWS 부스용으로 만든 산업안전 데모는 Unitree Go2가 공장을 돌며 위험 현장과 쓰러진 사람을 감지해 보고하는 구성입니다. 로봇 위 RGB-D 카메라 영상은 Amazon Kinesis Video Streams로 실시간 재생합니다. YOLO는 도움 요청·하트 같은 제스처를 인식합니다. 모델은 클라우드에서 학습하고 AWS IoT Greengrass로 Jetson Orin에 배포했습니다. Jetson Orin의 CPU·메모리·배터리 메트릭은 MQTT로 올려 Grafana 대시보드로 봅니다. 배터리가 낮으면 로봇을 충전 위치로 돌려보냅니다. 관리자는 웹페이지에서 원격 조종을 하고 에이전트 AI가 만든 순찰 보고서를 받습니다.

단순 크랙은 YOLO로 충분하지만, 학습 데이터가 없는 상황은 파운데이션 모델이 더 잘 추론할 수 있습니다. 그래서 엣지에서 YOLO와 결정 트리로 먼저 거르고 confidence가 낮을 때만 Amazon Bedrock VLM으로 보냅니다. 클라우드 왕복과 추론에 시간이 걸리기 때문입니다. 현장에 특화된 파운데이션 모델은 사실상 없으므로 현장 영상으로 테스트해 가장 정확한 모델을 고릅니다.

  • 원격 제어 — AWS IoT Core와 연결된 커맨드 컴포넌트가 MQTT 명령을 ROS로 넘겨 로봇 제어
  • 데이터 분리 — 필요한 RGB 데이터만 Amazon Kinesis Video Streams로, 학습용 이미지는 Amazon S3로 업로드
  • 순찰 보고서 — 위험 수준·권고 사항·근거 영상 포함, VLM이 영상·위치·메트릭을 묶어 상태 판단
  • 비용 — IoT 서비스가 가장 저렴, Amazon Bedrock은 토큰 과금으로 예상보다 저렴
  • 모델 후보 — Anthropic·OpenAI·NVIDIA 등 공급사 모델 제공, 언급된 Claude 모델명은 미확인
  • 전제 — 완성품이 아니라 직접 개발 필요, 네트워크 연결 전제

6Isaac Sim 학습은 로컬에서 정의 후 대규모 확장 때만 클라우드 사용

산업안전 데모에서는 미리 정의한 명령어·결정 트리 대신 AI 모델이 이미지를 보고 로봇 제어 메시지를 직접 만들어 전달하는 방식도 구현했습니다. Isaac Sim 환경에도 기존 하드웨어 시스템, 플래닝 알고리즘, 통신 규약을 그대로 구현할 수 있습니다. Amazon EC2 한 대에 ROS, Isaac Sim, 통신 프로토콜을 한 번 세팅하고 이를 복제해 씁니다. 최소 한 대는 현재 시스템에 맞춘 세팅이 필요합니다. Isaac Sim이 설치된 AMI는 무료이고 Amazon EC2 인프라 비용은 따로 냅니다.

여러 Amazon EC2의 파라미터와 리워드는 한꺼번에도, 개별로도 제어할 수 있습니다. 한꺼번에 제어할 때는 AWS Batch에 파라미터를 노출해 일괄 설정합니다. 개별 제어는 복제한 Amazon EC2에 SSH나 DCV 원격 GUI로 접속해 조작합니다. 다만 클라우드 학습은 로컬 PC에서 강화학습과 Isaac Sim을 돌릴 때보다 느립니다. 그래서 로컬에서 환경·알고리즘·보상을 먼저 정의하고 대규모 확장 테스트 때 클라우드로 옮기는 방식을 권장합니다.

  • 노출 파라미터 — Isaac Lab 환경 ID·로봇 종류·학습 에폭·태스크·노드당 GPU 수·이터레이션
  • Slurm — HPC 클러스터로 대규모 Amazon EC2를 직접 제어하는 대안
  • 다중 노드 — 노드 수 설정 가능, 노드별 경험 데이터를 공유 스토리지로 동기화해 하나의 모델 학습, 클라우드 스토리지라 매번 SSD 비우기 불필요
  • 공식 사례 — AWS Batch 다중 노드 병렬 작업으로 Isaac Lab 분산, 체크포인트는 Amazon EFS에 저장
  • 결과 확인 — 로그는 클라우드에서, 학습된 정책 동작은 Isaac Sim에서 바로 확인
  • 남은 과제 — 보상 설계·학습 시작 방법·환경 세팅 제어 방식 미정, 바닥에 물이 있는 경우처럼 예상 밖 상황은 룰 기반 플래너의 약점

7대용량 영상 회수는 SSD 교체가 가장 빠르지만 방식 미정

1시간 동안 움직이며 찍은 360도 영상을 무선으로 올리는 데 매우 오랜 시간이 걸렸습니다. 로봇과 도크를 이더넷으로 연결해 먼저 옮기고 도크에서 클라우드로 올리는 방식은 가능합니다. 하지만 로봇에서 엣지 장비로 보내는 이더넷 전송은 매우 느리고 불안정해 거의 쓰지 않습니다. 저장 장치를 물리적으로 떼어 옮기는 방법이 가장 빠릅니다. 대신 사람이 대기하다 떼어 내고 다시 꽂아야 합니다.

Jetson Thor 내부 SSD는 위쪽 부품을 먼저 떼어 내야 해서 교체가 번거롭습니다. 이 SSD는 원래 용량을 늘리려고 넣었고 데이터 회수용이 아닙니다. 그래서 외부 포트에 USB SSD를 달고 저장 로직을 넣어 떼어 내는 방안을 검토합니다. 특정 Wi-Fi 망에 붙는 순간 자동 업로드하는 방식은 밤새 걸렸습니다. 어떤 방식으로 갈지는 아직 정하지 않았습니다.

  • 압축 — NVIDIA 인코더 압축 시 압축 전후 10배 이상 차이 예상, 공식 수치 미확인, 코덱·비트레이트에 따라 변동
  • Jetson Thor 지원 — NVIDIA Video Codec SDK의 Jetson Thor 인코딩·디코딩 지원은 2026년 1월부터
  • 촬영 방식 — 포인트 이미지 촬영·타임랩스 촬영으로 데이터 경량화 검토(추정)
  • 충전 중 업로드 — 충전 시간 동안 업로드하는 방안 검토
  • 남은 조건 — 구동시간·압축률 측정 후 방식 선택

    Anthropic·OpenAI·NVIDIA 등 여러 공급사 모델 제공은 맞지만 Sonnet 5·Opus 5라는 Claude 모델명은 직접 확인하지 못했습니다.
  • AWS Marketplace: NVIDIA Isaac Sim™ Development Workstation (Linux)일치
    Isaac Sim AMI는 무료이고 g6e·g7e 인스턴스 비용은 따로 내며, SSH·DCV 접속(TCP 22·8443)도 설명과 같습니다.
  • Scale Reinforcement Learning with AWS Batch Multi-Node Parallel Jobs일치
    AWS Batch 다중 노드 병렬 작업으로 Isaac Lab을 분산하고 체크포인트를 Amazon EFS에 저장하는 구성이 설명과 일치합니다.
  • NVIDIA Video Codec SDK (NVENC/NVDEC)확인 불가
    2026년 1월부터 Jetson Thor 인코딩을 지원하지만 10배 이상 압축이라는 수치는 출처에 없습니다.

시사점

산업안전 데모 구성을 그대로 가져다 쓰기

데모는 Jetson Orin 위 YOLO를 AWS IoT Greengrass로 배포하고, 영상은 Amazon Kinesis Video Streams, 메트릭·명령은 AWS IoT Core·Grafana로 처리합니다. 이 구조는 이번 프로젝트의 센서·로봇 활용 구조와 거의 같습니다. 데모 구성에서 Jetson Orin만 Jetson Thor로 바꿔 시작하면 처음부터 설계하는 것보다 빠릅니다(추정).

VLM은 주행이 아니라 상황 판단에만 사용

룰 기반 플래너는 바닥에 물이 있는 경우 같은 예상 밖 상황에 약합니다. confidence가 낮은 경우만 Amazon Bedrock VLM으로 보내는 구성이 이 약점을 보완합니다. 다만 클라우드 왕복과 추론 지연 때문에 주행 판단에는 맞지 않습니다(추정).

제조사 개방 범위를 서면으로 확인

계단 전환 시 발 모터 제어와 자체 가감속 제어는 Ghost Robotics가 열어 주는 범위에 달려 있습니다. LIG Nex1이 지분 60%를 가진 모회사이므로 LIG Nex1 경로로 개방 범위를 서면으로 확인받는 것이 좋습니다(추정).

8월 중순 전에 구동시간과 압축률 측정

Jetson Thor 하드웨어 인코딩으로 장치에서 압축한 뒤 충전 중 도킹·Wi-Fi로 올리는 조합이 SSD 교체를 대신할 후보입니다. 구동시간과 압축률을 8월 중순 수동 운용 전에 재야 회수 방식을 고를 수 있습니다(추정).
